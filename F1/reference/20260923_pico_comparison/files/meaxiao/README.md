## v1.4.4：D070_01 底盘制动与保守速度档

本次只部署 **F1_D070_01**，不更新 D072/D070。摇杆与 A+B 默认速度模式共用上限：

| 上限 | v1.4.3 | v1.4.4 |
| --- | ---: | ---: |
| 前后 | 0.55 m/s | 0.35 m/s |
| 横移 | 0.45 m/s | 0.30 m/s |
| 转向 | 1.20 rad/s | 0.65 rad/s |

松杆或有效身体输入停止时继续使用 `zero_target`，不叠加软件减速尾巴、不用反向速度猛刹。
D070_01 原执行层角减速度 0.4 rad/s²；经用户授权已调整为 0.8 rad/s²，管理端和执行端读回一致。
这是影响原生遥控/导航的全局参数，**不在每次启动时自动写入**，也不复制到 D072。
首轮0.55档已完成部署后233项隔离回归及 `./start.sh --check`，用户现场确认手感很好。
随后用户要求提高到0.65，并明确接受停止角度可能超过15°、需要重新验收；最终验证见下方记录。
尚未重启底盘验证参数持久化，
如果重启后参数恢复为0.4，新预检会阻止启动；此时保持停机核对，不绕过检查。

`./start.sh --allow-motion` 和 `--check` 新增两端只读制动核对：管理源/执行端必须一致且不低于 0.8 rad/s²。
参数掉回旧值、服务不可达或估算超出预算时预检失败；不要删检查或直接抬高速度。
0.65 rad/s、0.8 rad/s² 的恒减速度估算约 15.13°，加 100 ms 响应预算约 **18.85°**。
经上述取舍，`braking_check.max_overrun_deg`设为20°**模型预算**，不是20°实机制动保证。
100 ms 是建模余量，不是网络硬保证；最终0.65档不再承诺≤15°。本次未进一步提高供应商角减速度。
负载、地面滑移、输入停更会改变停车效果；PICO 不会自动知道用户要停在180°。

正常启动方式不变。现场先空载低幅，再在安全空间逐步验证持续转向到稳定速度后的松杆；
可运行只读 `scripts/trace_chassis.py` 和 `scripts/analyze_chassis_stops.py` 记录过转。
分析器报告最大反馈积分偏移、低速持续时间；用`--max-overrun-deg`明确本次检验阈值（默认仍为原15°目标），
反馈过旧/样本断档/尾段不足不判通过；
它不能替代外部角度测量，也不自动下发运动。
双臂、精调、夹爪、录制、传输均不改。详情与回滚见 [本次验证记录](reports/verification_v1.4.4_2026-09-18.md)。

## v1.4.3：慢速精细映射与手腕抑抖

> 2026-09-16 同版本补丁：缩小精调速度区间、修复超时保持后的恢复流程并细分停止诊断。
> 已备份部署到 D070，候选及部署后均通过 211 项隔离回归，未自动启动遥操。
> 详见 [本次补丁记录](reports/verification_precision_holds_2026-09-16.md)；真实末端精度与手感仍需现场验收。

保持你已确认合适的低延迟输出档 **30°/s、100°/s²、600°/s³、250 Hz**，新增 IK 前的
自适应位姿滤波与连续变倍率；不新增按键，不改夹爪开合、X+Y、底盘/腰部与数采操作。

- **慢速精调：** 估计手柄平移速度不超过 5 mm/s 时按 0.2 倍增量映射，例如缓慢移动手柄 5 mm，
  滤波收敛后对应约 1 mm 的 IK 平移目标；手腕慢速旋转按 0.25 倍映射，并抑制姿态噪声。
- **快速移位：** 倍率随速度连续恢复至 1.0，不会突然切档。它是增量映射，
  不是任何速度下都保持绝对 1:1 位移；长距离若始终缓慢移动，也会保持小倍率。
  快速段已积累的位置不会因减速而被重新缩放或拉回。
- **微小输入不中断：** 不给手柄位移设“攒够再跳”的空间死区；双臂上游数值死区从
  0.03° 降到 0.0002°，让微小连续目标能够通过。抑抖放在输入端，不靠大死区截断运动。
- **松 Grip / X+Y / 重连 / 菜单重定向：** 每只手独立清空滤波参考，首次接管零增量，
  保留未操作臂保持。`PRECISION_INPUT_HOLD` 表示跟踪跳变/输入间隔异常，
  对应臂保持直到松开 Grip 后重新建立参考，不自动追赶异常输入。

配置在 `config/control.json` 的 `precision` 中，常用项：

| 配置 | 默认值 | 意义 |
| --- | ---: | --- |
| enabled | true | 精细输入映射开关；停止遥操后改动，重启生效 |
| position_min_gain | 0.2 | 慢速平移倍率：5 mm 手柄位移约对应 1 mm 目标 |
| rotation_min_gain | 0.25 | 慢速旋转倍率 |
| position_slow_m_s / position_fast_m_s | 0.005 / 0.04 | 5 mm/s 以下全精调，5～40 mm/s 连续过渡，40 mm/s 以上稳态倍率 1.0 |
| rotation_slow_rad_s / rotation_fast_rad_s | 0.04 / 0.35 | 约 2.3～20.1°/s 为旋转倍率过渡区间 |
| filter_position_slow_m_s / filter_position_fast_m_s | 0.025 / 0.15 | 独立控制平移滤波带宽，不是精调倍率边界 |
| filter_rotation_slow_rad_s / filter_rotation_fast_rad_s | 0.15 / 1.0 | 独立控制姿态滤波带宽，保留抑抖 |
| min_cutoff_hz / max_cutoff_hz | 3.5 / 15 | 慢速抑抖 / 快速减小滤波滞后 |

**延迟与精度边界：** 合成匀速测试中，新增位置滤波本身的稳态等效滞后约为慢速 41 ms、
快速 6 ms；倍率过渡及已有 IK/轨迹链路另外影响响应，不能把两者简单相加当实机延迟。
本次阈值下，8 Hz 合成抖动的位置 RMS 从 0.707 mm 降至 0.068 mm、姿态 RMS 从 0.353° 降至 0.041°，
这些只证明软件对该输入的抑制效果。**1 mm 目标可表达，不等于真实夹爪端点达到 1 mm 精度，
更不代表微米精度或已能穿针。** 当前 IK 使用 `arm_L_Link7` / `arm_R_Link7`，
工具/针尖 TCP 标定、机构回差、实际跟踪误差与视觉测量必须另行验证。

使用仍为 `./start.sh --allow-motion`。先空载小幅移动、停手保持、分别松/扣 Grip，
再在有标定尺度的测量条件下检查末端 1 mm 往返微调；不要直接把针尖接触任务作为首次验收。
需要恢复 v1.4.2 的输入手感时，停止后将 `precision.enabled` 设为 false，
并将顶层 `joint_deadband_deg` 恢复为 0.03；`arm_output` 保持 100/600，不必重装环境。
验证与部署状态见 [v1.4.3 精细映射验证](reports/verification_precision_v1.4.3_2026-09-15.md)。

### 2026-09-16：如何区分精调变慢与保护停止

**没有突然切换的二挡模式。** 原版低于 25 mm/s 都是最低倍率，需 150 mm/s 才恢复全倍率；
现将这两个边界降至 5 / 40 mm/s。平移稳态示例：5 mm/s → 0.20 倍、20 mm/s → 0.51 倍、
30 mm/s → 0.84 倍、40 mm/s → 1.00 倍。速度估计与倍率均经过低通，阈值不是原始帧速度；
减慢会连续减小增量，不应把手臂锁死。倍率门槛和滤波带宽已分离，避免门槛降低同时放大抖动。

| 日志标识 | 含义与处理 |
| --- | --- |
| `WAIT_XR_FRESH_FRAMES` / `WAIT_XR_RELEASE_CONTROLS` | XR 位姿/时间戳无效、倒退或停更；新版显示 `last_fault` 和停更时长。松开控制，等待 `XR_READY`，再重新扣 Grip；不会追赶断流期间的旧动作 |
| `ARM_OUTPUT_HOLD_LATCHED` | 桥接目标过期或输出调度停顿，不等于碰撞。新版分别输出目标年龄和调度间隔；松开两侧 Grip，连续未启用指令与输出节拍稳定至少 200 ms 后显示 `ARM_OUTPUT_REARMED`，保持原位置等待重新扣 Grip |
| `ARM_COLLISION_HOLD_LATCHED` | 候选目标进入模型保护包络；停止对应臂，确认安全并松开相应 Grip 才能重新接管。新增 `ARM_COLLISION_DIAGNOSTIC` 保留候选/实测关节角、碰撞对、包络及阈值，便于离线核对 |
| `PRECISION_INPUT_HOLD` | 单臂位姿突跳或精调输入时钟异常，松开该臂 Grip 后重建参考 |

**规划失败或时钟倒退仍需检查后 X+Y/重启，不按普通超时自动解除。** X+Y 会实际移动，请先确认路径安全。
上述恢复不削弱 XR 新鲜度、反馈新鲜度、逐臂按键和碰撞门控；重新收到一个活动指令不能解除超时锁存。

本次日志中既有模型包络拦截，也有实际 XR 停更，不能统称“虚假碰撞”。例如 Link5 对的
`clearance=-0.00236m` 已扣除了 10 mm 手臂外扩，约对应 7.64 mm 原始网格间隙，
不是实体穿透 2.36 mm；而且检查的是将要执行的目标，不是肉眼观察的当前姿态。
**不以肉眼未接触为由去掉模型包络、放宽阈值或延长失联放行时间。** 持续出现 XR 停更应检查头显—PC Service
链路；持续出现同一碰撞对，应依据新日志核对模型、关节映射与实际工具外形，而非反复强行接管。

**2026-09-16 断控排查仍待闭环：** 重新连接后的同步采样确认存在输入流停更，不能用头显显示
70～90 fps 证明机器人端数据新鲜。关闭 D070 Wi-Fi 省电并清理旧 PC Service 会话后，典型间隔改善，
但后续 90 秒仍有 17 次超过 250 ms；尚不能宣称已经修复。失联时先释放全部控制，
持续按 X+Y 既不能恢复数据链路，也不能满足重连释放条件。详细证据、临时设置及回退见
[XR 链路诊断](reports/diagnosis_xr_link_2026-09-16.md)；勿通过放宽失联阈值代替链路修复。

## 2026-09-15 上一轮连续运动反复加速修复（算法保留，输出限值见上节）

本节取代上一轮“250 Hz 两级 12 ms 平滑”方案。离线复现确认：旧输出虽然限制了
单步位移，匀速目标仍产生周期性速度起伏；只提高发布频率不足以解决卡顿。
现在上游仍按目标 50 Hz 做 IK / 轨迹规划 / 碰撞批准，末端输出以目标 250 Hz
持续保留位置、速度、加速度状态，按实际时间间隔执行 **30°/s、75°/s²、300°/s³**
约束，不逐包从静止重启。另修复碰撞计算略超时后额外等待完整周期的问题。

同一组合成 25°/s 匀速目标，旧输出稳态速度范围为 21.64～30.00°/s，
新输出为 24.97～25.15°/s。这是软件复现，不是实机振动或精度指标。
该方案有跟随代价：20°/s 合成匀速测试中输出层等效滞后约 0.27 s（约 5.4°），
不能沿用旧版“约 24 ms”的描述；没有为了消除滞后而放宽运动限值。

- **松开任一侧 Grip：** 对应臂在桥接端保持最后电机位置指令并清除待执行目标，另一臂仍可遥操。
  再次接管从该臂新鲜反馈重建上游参考；X+Y 后首次接管仍保留复位完成交接机制。
- **碰撞拦截：** 被拦截臂保持，不能在 Grip 一直按住时自动“停住—追赶”。看到
  `ARM_COLLISION_HOLD_LATCHED` 后松开对应侧键，确认现场无碰撞风险，再重新扣住；不关闭保护。
- **输入/调度异常：** 150 ms 无新目标、输出循环停顿超过 50 ms 或规划失败，
  出现 `ARM_OUTPUT_HOLD_LATCHED` 并保持；活动指令不会自行解除。2026-09-16 补丁允许普通超时在
  连续未启用与健康节拍后保持原位置重新待命，详见上节；规划失败/时间倒退仍需检查后复位。
- **正常启动：** 更新前结束录制并 `./stop.sh`，整体同步两端补丁；下一次直接
  `./start.sh --allow-motion`，不增加授权口令。录制频率、底盘和 body_j3 参数不改。

`logs/teleop.log` 的 `ARM_OUTPUT_TIMING` 查看上游实际节拍，`logs/bridge.log` 的
`ARM_SERVO_OUTPUT` 查看输出节拍；复位暂停不再混入输出最大间隔。Grip/碰撞/超时保持
优先于平滑约束，所列动态限值不代表急停过程或物理电机响应的保证。
碰撞检测仍在上游，输出轨迹不替代连续路径碰撞验证；实际带电手感、满负载时序及机械振动
仍需现场验收。详见 [连续运动修复与验证](reports/verification_arm_surge_2026-09-15.md)。

## 2026-09-15 机械臂接管补丁（仍为 v1.4.2）

修复 X+Y 后首次按侧键追赶旧位置的问题：先等待桥接器确认复位指令发送完，
再用连续新鲜反馈判断已停稳；接管沿用复位最终位置指令，不跳回带残差的反馈。
每侧侧键独立重建增量基准，首次按下保持当前位置；只有后续手柄位移才推进目标，
未按侧键的另一臂仍保持最后批准位置。

遥操端到桥接器的 UDP 发送改为轨迹规划与碰撞批准同一时钟，每周期发送一次，保留原来的限速度、
限加速度、限 jerk 和碰撞保护；IK 超过 150 ms 未更新时保持，不积压历史帧。
`logs/teleop.log` 新增 `ARM_OUTPUT_TIMING`，显示实际发送 Hz、最大间隔 ms、最大关节步长 °，

使用方式不变：`./start.sh --allow-motion`。X+Y 仍然按下即开始复位，松开 X+Y、

## v1.4.2补丁：按场景采集，传输服务随start/stop启停

**日常只需改一个YAML，在机器人执行start/stop，不再手动常驻6000d接收服务。**
本节覆盖此前“stop.sh后继续运行传输队列”的旧说明；版本仍为v1.4.2。

### 1. 开始一个子任务前，修改哪里

在对应机器人项目的 **config/collection.yaml** 配置场景。6000d源码中的同名文件是部署模板；
修改模板后还需同步到目标机器人，运行中的会话不会自动切换场景。

~~~yaml
scene: mm
task: F1 PICO teleoperation
local_base: mocap_data
central:
  dataset_base: /media/user/069dd146-6f88-4f29-b859-245b1c012179/pico/mocap_data
  host: 192.0.2.33
  port: 22222
  user: user
  identity_file: config/private/transfer_control_ed25519
  known_hosts_file: config/private/transfer_control_known_hosts
  dashboard: true
~~~

| 配置 | 含义 / 修改时机 |
| --- | --- |
| scene | 子数据集名，例如mm、pick；用英文、数字、下划线或连字符 |
| task | LeRobot任务文字；同一已有子数据集不能中途改任务，换任务应新建scene |
| local_base | F1项目内的相对目录；最终路径为local_base/scene/mocap_data |
| central.dataset_base | 6000d数据集基目录；最终路径为dataset_base/scene/mocap_data |
| central.host / port / user | 已配对的私有SSH控制入口，不是网页地址；日常换场景不需要修改 |
| identity_file / known_hosts_file | 本机器人专用控制密钥与服务器主机指纹；不要复制其他机器人的私钥 |
| central.dashboard | true：采集时自动启动中央网页；false：不为本会话请求网页 |

以mm为例：

~~~text
F1：
/home/user/meaxiao/pico/mocap_data/mm/mocap_data

6000d：
/media/user/069dd146-6f88-4f29-b859-245b1c012179/pico/mocap_data/mm/mocap_data
~~~

只把scene改成pick，两端都会使用各自的pick/mocap_data，mm不受影响。
中央基目录允许在已授权磁盘的pico目录内另建数据集；跨磁盘/跨授权根目录需要管理员重新授权，
不能靠机器人配置获得任意服务器目录的写权限。凭据和场景路径不再通过start.sh中的旧TRANSFER_DESTINATION变量配置。

### 2. 每次使用：在F1执行两条命令

先确认现场安全、机器人服务正常，并确认YAML中的场景正确：

~~~bash
# ssh F1_D070_01：user@ms-thor
cd /home/user/meaxiao/pico
./start.sh --allow-motion
~~~


程序会依次：

1. 检查并冻结本次场景配置，绑定本地子数据集与中央归档路径。
2. 经受限SSH登记本机器人的会话，自动唤起6000d接收服务；按配置启动网页。
3. 启动F1本地队列，并继续执行原有的XR、相机、反馈、初始姿态等安全检查。
4. 录制器、预检和队列使用同一份冻结配置，避免“录像写A目录、上传却读B目录”。

启动日志会显示“场景=mm”“本地=…”“中央=…”以及中央活跃机器人名单。
连接中央失败会报错，不会把“请求已发出”当成“服务已启动”。--check只检查，不开启中央会话。

正常录制：X双击开始，Y双击结束，B单击保存；X+Y复位仍属于录制内容。
每条完整保存后自动进入队列；不需要手动rsync、再按B或打开另一条上传命令。

结束时在同一机器人执行：

~~~bash
./stop.sh
~~~

先结束并保存想保留的录制，再stop。需要停止机器人运动时不要为了等上传而延迟stop。
stop会停止遥操/录制相关进程、关闭F1传输队列，再通知6000d退出本机器人的会话。
本次未传完的数据、清单和回执均保留，stop不是删除或清空数据的操作。

### 3. “全部关闭”与多机器人同时采集

默认按会话计数关闭，避免一台机器人的stop中断另一台正在采集的机器人：

| 当时的情况 | 某台F1执行stop后的结果 |
| --- | --- |
| 只有这台机器人在采集 | F1队列退出，6000d接收和网页服务都停止 |
| D070、D072同时采集，D070先停止 | D070退出；保留D072仍需要的中央服务 |
| 最后一台机器人停止 | 6000d接收与网页服务全部停止 |
| 网络断开，中央无法确认stop | 本地队列先停止，stop返回错误并保留会话记录；网络恢复后重试stop |

这里“全部关闭”指本项目的传输工作进程、接收进程和受管网页进程。
**系统SSH与私有Tailscale控制入口必须保持可达**，否则无法从机器人重新唤醒6000d；
这些是现有远程连接基础设施，不是后台轮询/传输数据的进程，不开放公网网页接口。

F1每15秒发送会话心跳，中央租约为90秒。意外关机或失联且无其他活跃会话时，
中央接收器通常会在最后心跳后约90–95秒请求关闭服务（不是硬实时保证）。
正常stop不等待租约到期，而是立即请求关闭并检查返回结果。
中央不可达时不能谎报“已全部关闭”；应恢复网络后重试。

运行中不要直接改YAML然后重复start：它不会切换已有遥操会话。
**切换顺序必须是stop → 改YAML → start。** stop使用启动时冻结的会话，不会被后来修改的YAML误导。
本补丁没有改变现有XR PC Service保留策略或机器人系统节点的生命周期。

### 4. 关闭后再次启动，编号会怎样

同一个scene和原目录继续使用时：

- F1本地数据集从原有总数继续追加，例如已有0–9，下一条为10。
- 6000d按中央原有总数继续追加；如果同时有其他机器人，中央编号不必等于本地编号。
- 幂等键为“物理机器人ID＋本地数据集UUID＋本地episode”，重启不会改变UUID或重复追加已入库条目。
- 不同scene分别拥有数据集和连续编号，例如mm的10与pick的0互不覆盖。
- 两台机器人各有本地episode 0，中央在同一scene内分配不同编号，并记录来源。

不要删除UUID、transfer_state、manifest、ACK或中央provenance来“重新开始编号”。
想创建新数据子集时改scene；不要用清空旧数据目录的方式换任务。

### 6. 传输原理与数据不混淆的保障

~~~text
F1：完整保存 → 提交索引 → 冻结文件/哈希 → 本地持久队列
                                             ↓ 6000d通过SSH拉取
中央：接收临时文件 → 校验完整性 → 分配编号 → 原子发布 → 回执
                                                ↓
                                   网页读取中央最终子数据集
~~~

- 保存判定使用录制器提交锁及最终meta/info.json，不读取未保存的暂存录像。
- 校验覆盖Parquet、三路视频、alignment补充帧的长度/哈希、数据契约、帧数与时间轴；失败不发布。
- 视频不重编码，动作/状态/源时间戳保持原值，只重映射中央episode、全局帧和task索引。
- 中央先写完整不可变修订，再原子切换mocap_data入口；中断中的半成品不作为正式数据出现。
- 中央provenance.json记录全局编号、F1_D070/D071/D072、本地UUID/编号和文件哈希。
- 回执到达后只清理额外传输副本，F1原始子数据集不自动删除。

中央mocap_data是指向完整修订的符号链接。训练启动时可用readlink -f固定某个修订，
避免训练过程中数据增长；备份要复制实际内容，不能只备份一个符号链接。

2026-09-18 已由现场确认：独立 SSH 到 `user@192.0.2.1:22` 的转发可用；当时 VS Code 转发条目存在但请求超时，具体内部原因未确定。新增 [windows_review.ps1](scripts/windows_review.ps1)，不再依赖 VS Code 的端口恢复。

先结束之前手动 `ssh -N ...` 的 PowerShell 隧道，并删除 VS Code 中的 **18976** 转发，保留其他端口。脚本不会抢占端口或杀死已有 SSH/VS Code 进程。

```powershell

# 安装后检查：网页开启时应显示 HTTP_READY。
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\PicoReviewTunnel\windows_review.ps1" -Mode Status
```

安装会再请求一次6000d账户登录，以登记本机新生成的专用公钥；密码只输入 SSH 提示，不会写入文件。严格沿用已经验证的服务器主机指纹；指纹缺失/变更时停止，不自动信任陌生服务器。看到 `INSTALL_OK` 表示配对与自启入口已安装，**实际网页可达仍以 `HTTP_READY` 为准**。

自动行为与安全边界：

- 安装目录为 `%LOCALAPPDATA%\PicoReviewTunnel`；当前用户“启动”文件夹创建 `PicoReviewTunnel.lnk`，登录后后台运行，不依赖 VS Code 或手动保留终端。专用密钥不上传、不复制其他设备的私钥。
- 专用密钥为无人值守使用不设口令，用 Windows 目录 ACL 限制当前用户及 SYSTEM；不保存账户密码或网页 access.token。本机账号/管理员被控制时仍可能读取密钥，不宣称绝对安全。
- 服务器为此公钥禁用交互命令、PTY、agent/X11/rc，固定命令仅返回配对标记；本地转发目标只允许 `127.0.0.1:18976`，反向监听也限制为同一回环端点，不授予任意端口权限。不修改系统 sshd 配置或其他用户权限。
- Windows 仅监听 `127.0.0.1:18976`，跨机器段 SSH 加密。保留网页密钥登录和 Host/Origin 检查，不自动填充/泄漏 token；Cookie 过期后仍可能需要重新登录网页。
- 每15秒进行 SSH 存活检查、连续3次失败后退出重连；重试间隔3～30秒，网络恢复后继续尝试。这不是断网/休眠期间仍可用或固定时间恢复的保证。
- 同一Windows会话使用互斥锁防重复运行；端口被其他程序占用只记录 `PORT_BUSY` 并等待，不结束未知程序。不要再同时开启 VS Code 的18976转发。
- 不启动6000d网页、机器人或数据接收服务。最后一台机器人 `./stop.sh` 关闭中央网页后，隧道可保持连接，但网页暂不可用；下一次采集会话启动网页后仍使用原地址。

日常控制（Windows PowerShell）：

```powershell
$PicoReviewScript = "$env:LOCALAPPDATA\PicoReviewTunnel\windows_review.ps1"
# 看状态、监听端口和最近日志
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $PicoReviewScript -Mode Status
# 暂停隧道；保持暂停，即使下次登录也不自动恢复

# 恢复隧道及后续登录自启

# 恢复并在检查网页就绪后，用默认浏览器打开
```

  localhost仍不能防御本机root或账号/浏览器失陷，因此密钥登录不可省略，也不承诺绝对安全。

### v1.3.9 最新补丁：停止目标立即归零（2026-09-14）

现场只读记录确认：循环已稳定 50 Hz，但松杆后旧软件仍输出约 0.20–0.32 s 非零
转速，且底盘反馈在命令归零后还会继续变化。当前默认
`chassis.neutral_stop_mode=zero_target`：摇杆轴回中或身体对应速度进入死区时，
**该轴下一控制周期直接发送零速度目标，不再叠加一段软件减速轨迹**。
不发送反向补偿、不触发急停/驻车服务、不猜测 180° 目标；其他仍有输入的轴不重置。

A+B 与摇杆共用启动即时目标、速度/加速度/jerk 上限和停止策略，默认身体模式仍为
`velocity`，人停止后不追赶旧位置。身体输入需等新鲜姿态帧识别停止，不能承诺与
摇杆开关具有相同传感延迟。松开 A+B、失联、反馈超时等原有零命令保护保留。

**重要区别：立即的是零速度指令，不是车轮速度。** 正常启动/非零目标变化仍经过
Ruckig；停止边沿不再承诺软件加速度/jerk 连续，而由供应商底盘执行制动。
因此必须空载、小幅、有人值守验证实际平稳性；不能以指令为零宣称已经物理停稳，
也不能保证“170° 松杆必定停在 180°”。负载、地面、转速不同，制动角度会变化。
需要旧的纯软件连续减速时，可将 `neutral_stop_mode` 改为 `profiled` 后重启，
但会恢复这段软件拖尾。版本保持 v1.3.9，不需要重装 uv 环境。

如仍迟滞，运行下面调度补丁中的只读 `trace_chassis.py` 记录，新增保存底盘源时间戳、

## 这次优化解决了什么

- 完整映射：笛卡尔位移比例为 `1.0`，PICO 位移按 1:1 映射，不再因原 `0.12`
  缩放只能走很小范围；Grip 仍是相对位姿离合，松开再握紧可在当前位置重建零点。
- 转身不反向：控制器位姿先转换到随头显 yaw 连续旋转的人体局部坐标系，并消除
  头显整体平移；操作者和机器人转身后，向右移动右臂仍对应机器人局部向右。
- 平滑跟随：50 Hz 控制时钟上对 IK 目标执行 5 Hz 低通和 `0.03°` 关节死区，
  再用 Ruckig 在线生成受限轨迹。默认上限提高为 `30°/s`、`75°/s²`、`300°/s³`，
  三项同比例提高以缩短跟随延迟而保持连续加速度。
- 安全提交：轨迹的每个 20 ms 候选点先经 CollisionGuard；只有通过的左/右臂
  才提交。反馈超过 `0.5 s`、NaN/Inf 均拒绝；大于 `3°` 的原始 IK 目标差只记录
  诊断，实际关节步仍由低通、Ruckig 和逐点碰撞检查限制，避免目标门禁永久锁死。
- 碰撞确认：凸包只作快速保守筛选；接近阈值时用原始三角网格复核凹空，仍保留
  10 mm 手臂表面外扩、`-2 mm` 阈值和 Link7 末端加长保护。
- 动态会话初始位：每次 `--allow-motion` 在启动任何控制发布者之前，从
  `/hal/joint_states` 捕获静止的 22 个具名关节，并从两路夹爪状态话题捕获左右
  OmniPicker 的单主动轴，共 24 个真实执行轴作为本次会话初始位；`hand_*` 只是
  未安装 OmniHand 的接口占位项，明确忽略。程序不再读取
  `target_left/reset_left`，启动本身不会移动机器人。
- 安全复位：X+Y 在首次检测到组合键的 20 ms 控制帧内立即接受，不需要长按；复位在
  独立线程执行，默认轨迹下限由 3 秒缩短为 0.6 秒，位移较大时仍按速度上限自动延长。
  仅让双臂 14 轴和 `body_j3` 经 minimum-jerk 插值回到本次启动快照，头部、其余躯干
  关节和左右 OmniPicker 均保持当前状态。路径先经 CollisionGuard，完成后再把 Placo、
  原始目标、最后安全目标和 Ruckig 的位置/速度/加速度一次性重置；失败则保持暂停。
- 可迁移：网络、初始姿态、滤波/轨迹参数、数据路径都在 `config/`；现场 episode
  写入 `mocap_data/<scene>/mocap_data/`，日志写入 `logs/`，PID 和会话初始位写入 `run/`。
- 底盘位姿闭环：人体相对起点的 X/Y 位移和 yaw 转角以 1:1 映射为机器人目标位姿，
  `/move/State.odometry` 提供实际位置反馈；人在停下后，只要仍按住 A+B，机器人会
  继续平滑消除剩余误差，而不是要求人体持续移动。
- 即时但平滑：位置目标不再先经过低频输入滤波，人体开始运动后的首个 50 Hz 控制帧
  即产生非零目标；实际速度仍由 Ruckig 限速度、限加速度和限 jerk，安全性不依赖延迟。
- 双摇杆底盘：左摇杆 `Y/X` 分别映射底盘 `linear.x/-linear.y`，右摇杆 `-X`
  映射 `angular.z`；径向死区抑制漂移，回中速度经 Ruckig 连续减速。
- 躯干俯仰：A 长按超过 `0.35 s` 后，以当前头显俯仰和实时 `body_j3` 为相对零点；
  目标在 50 Hz 下经 CollisionGuard 批准，再由**唯一一个** 1 kHz Ruckig 输出线程
  重采样，保持 `6°/s`、`15°/s²`、`60°/s³` 上限和 `KEEP_LAST(1)` QoS。松开 A
  不回弹，每次再按都会在当前姿态重新建零。
- 直接 LeRobot v3：每组三路全新图像触发一行 30 Hz 数据，同步采样 22 个本体关节、
  左右 OmniPicker、底盘实测/指令
  `x/y/yaw` 速度以及头部、左右腕部 JPEG，相机使用 H.264 视频，状态与动作写入
  Parquet；异步编码队列只缓冲不丢帧，队列溢出或任一时间/帧数校验失败保留到恢复目录。
  只有 B 单击确认且全部校验通过后才加入正式 LeRobot 数据索引。

这些机制改善指令连续性和手柄分辨率，但不能仅凭软件测试承诺完成穿针、微小
螺丝等任务。此类能力还受末端执行器间隙、相机标定、深度感知、网络抖动、负载、
关节回差和操作者训练影响，必须用实物任务、多次试验和视频/遥测单独验收。

## 每次启动（有人值守）

现场确认机器人和周围空间后，日常只需执行：

```bash

cd /home/user/meaxiao/pico
./start.sh --allow-motion

```

`--allow-motion` 先确保输入用 PC Service 运行，再自动执行身份、ROS、底盘、相机和磁盘预检。
PICO 可在命令之前、执行中或执行后连接；未连接时停在 `WAITING_FOR_PICO`，
不会因为超过一秒而失败，也不会启动运动控制进程。PICO App 勾选 Head、Controller 并点击 Send，
松开按钮、Grip、扳机并让摇杆回中；连续新时间戳和有效三路位姿、约 0.2 秒中立输入后继续。
等待超过 5 秒会在连接成功后重新检查机器人，避免使用过期预检结果。
随后读取 22 个具名关节和两路
OmniPicker 状态，要求连续
3 帧总摆动不超过 `0.25`（关节为度、夹爪为位置百分比），保存到
`run/session_initial_pose.json`，再以该快照初始化
IK 并启动 UDP→ROS 桥。启动阶段不发送关节运动；Grip、A 和 A+B 仍分别是双臂、
`body_j3` 和人体跟随底盘的运行时按住启用键。

等待期间可 Ctrl+C 或在另一终端执行 `./stop.sh` 取消；取消后不会因头显稍后连接而自行启动。
重复执行启动命令，完整会话返回 `PICO_ALREADY_RUNNING`，启动/停止处理中返回
`PICO_ALREADY_STARTING_OR_STOPPING`；这些提示不是重新完成了一次预检。
只剩部分进程时会拒绝叠加启动，先完成数据确认并执行 `./stop.sh`。

运行中位姿无效、时间戳倒退或超过 0.25 秒未更新时，输入门控关闭：底盘目标归零，
双臂和俯仰目标保持，不回放缓存按键，夹爪保留上一有效扳机意图。重新连接后松开控制并回中，
由新帧恢复输入，双臂依据实时关节反馈重新建立映射；本次 X+Y 复位快照不改变。
此功能不等于网络断开时物理立即停车，也不包括 PC Service 崩溃或底层机器人服务故障的自动修复。

`./start.sh --check` 和 `./shadow.sh 45` 仍保留用于版本升级、异常排障或隔离测试，
但日常停止后重启不再要求运行它们，也不再要求 `scripts/authorize_motion.sh`。
正常 `./stop.sh` 会保留 XR PC Service 与头显连接，因此同一次作业内再次启动不需要
重新点击 Send；维护或关机前需要连 PC Service 一并关闭时执行 `./stop.sh --stop-service`。
若输出 `PICO_PROCESSES_STOPPED_RECOVERY_PENDING`，表示进程已停止但底盘模式/实体手柄恢复失败，
不能据此认定物理停车；恢复标记保留，链路恢复后再运行 `./stop.sh` 完成恢复。

若 Shadow 显示 `packets=0`，先确认 PICO 应用内至少已勾选 Head、Controller，
点击 `Send`，唤醒两只手柄并按住任一侧 Grip；这表示 XR 输入尚未送达，不是机械臂
轨迹参数问题。F1_D070、F1_D072 开机后会由 `f1_startup.service` 自动运行底层
`start_all.sh`，不要再手工执行；预检要求控制订阅者、本机 motor/camera 节点
各为 1，且三路相机均能取得实时帧，发现重复进程时必须先清理再遥操作。

若只有 `/move/State` 检查失败，确认机器人文件
`/etc/ros/cyclonedds/cyclonedds.xml` 已绑定底盘网口（D070 为 `enP3p1s0f1`，D072
为 `eth0`）。`scripts/env.sh` 会自动采用该配置，避免多网卡环境误选 WLAN；配置在
其他位置时可在启动前设置 `F1_CYCLONEDDS_URI=/path/to/cyclonedds.xml`。
预检还要求 `/move/SetControlMode` 有且仅有一个服务端、
`/move/ManualMoveCmd` 有且仅有一个底盘订阅者；仅能读取 `/move/State` 不代表控制
链路完整。启动失败会输出 `STARTUP_FAILED`；若已经接管机器人，会尝试恢复底盘模式
及物理手柄节点。链路故障使恢复失败时保留恢复标记并明确报错，不会强行恢复其他控制发布者。

F1_D070 上 PC Service 对 PICO 的外部监听端口是 `63901`，本机 Python SDK 使用
回环端口 `127.0.0.1:60061`。PICO 应选择界面当次自动发现到的 F1 网卡地址；不要
硬编码旧 DHCP 地址，也不要把 `60061` 当成 PICO 的外部连接端口。项目内部
teleop→bridge/recorder 的 `8888/8899` 固定绑定 `127.0.0.1`，不随 Wi-Fi 地址变化。
PC Service 或 PICO App 重启后必须重新点击 `Send`，仅显示设备/IP 并不表示姿态流
已经发送。

XR 服务由 `scripts/ensure_xr_service.sh` 统一启动，日常一键启动会自动调用。单独准备
输入服务并检查输入（不下发运动命令）：

```bash
bash scripts/ensure_xr_service.sh
source scripts/env.sh
.venv/bin/python scripts/check_xr.py --seconds 30
```

`START_POSE_BLOCKED` 表示模型拒绝当前捕获姿态，不是网络故障。
可以单独执行 `.venv/bin/python scripts/check_start_pose.py --check-path` 查看碰撞对。
不要修改碰撞阈值或关闭保护以跳过此错误。`XR_DATA_INVALID` 表示 PICO 尚未点击
Send、手柄休眠或位姿无效；解决输入后重新运行同一条启动命令即可。

紧急停止软件链：

```bash
./stop.sh
```

`stop.sh` 先停止 ROS 命令桥，再停止遥操作生产者；若机器人仍异常运动，立即按
物理急停，不能依赖 SSH 或软件停止。回初始位会产生真实运动，只可在现场清空
空间后按 `X+Y`。

## PICO 操作语义

| 操作 | 功能 |
| --- | --- |
| 左/右 Grip | 对应手臂离合；按住才跟随，松开保持 |
| 左/右 Trigger | 对应夹爪开合 |
| 左手柄三横线菜单键 | 重定向双臂局部坐标和人体跟随底盘基准 |
| 左摇杆 Y/X | 非 A+B 模式下控制底盘前后/横向平移 |
| 右摇杆 X | 非 A+B 模式下控制底盘自身顺/逆时针转动 |
| 持续按住 A（不按 B） | 启用头显俯仰到 `body_j3` 的相对跟随；松开保持当前姿态 |
| 持续按住 A+B | 启用身体跟随底盘并覆盖摇杆；松开后回到摇杆模式 |
| X 双击 | 开始一个 LeRobot v3.0 episode |
| Y 双击 | 停止当前 episode，等待保存/丢弃确认 |
| 录制结束后 B 单击 | 保存该段并回到可录制状态；单击需等待 0.35 s 排除双击 |
| 录制结束后 B 双击 | 丢弃该段并回到可录制状态 |
| X+Y | 立即让双臂 14 轴和 `body_j3` 回到本次启动自动捕获位（真实运动） |
| 单独一次 X 或 Y | 无动作；只有各自双击才有录制语义 |

X+Y 复位时先松开两侧 Grip 和 A+B，再同时按下 X+Y，首次采样即接受请求，无需保持。
日志会立即出现 `RESET_COMMAND_ACCEPTED`；小位移复位最短约 0.6 秒完成，位移较大时
为遵守双臂和 `body_j3` 速度限制会自适应延长，这不是按键检测延时。复位不会发布
夹爪、头部或 `body_j1/j2/j4/j5` 指令；如果当前正在录制，复位轨迹会继续写进同一个
episode，录制状态不会改变。等待双臂和 `body_j3` 停止后可检查：

```bash
grep -E 'RESET_REBASE_OK|RESET BLOCKED' logs/teleop.log | tail -5
```

只有出现 `RESET_REBASE_OK` 才重新按 Grip；若出现 `RESET BLOCKED`，保持松开 Grip，
确认底层反馈和复位空间后重新按一次 X+Y。该流程不会恢复复位前的旧目标。

整机转身后无需停止程序：双臂坐标会自动随头显 yaw 更新。若 PICO 发生定位重置、
操作者与机器人朝向重新对齐或希望主动清零底盘累计目标，松开 A+B 后短按左手柄
摇杆旁的三横线菜单键；日志出现
`LOCAL_FRAME_RECENTER_ARMS_OK` 和 `LOCAL_FRAME_RECENTER_CHASSIS_OK` 即表示生效。

数据集按 `config/collection.yaml` 写入子场景目录；默认是 `/home/user/meaxiao/pico/mocap_data/mm/mocap_data`。建议另开SSH终端执行：

```bash
cd /home/user/meaxiao/pico
./recording_console.sh
```

该终端持续显示开始/结束、录制时长、有效 fps、丢帧数、三路视频分辨率/帧数和
保存路径。Y 双击后必须等待提示，再用 B 单击保存或 B 双击丢弃；未确认前 X 双击
不会开始下一段。保存后运行只读结构检查：

```bash
.venv/bin/python scripts/check_lerobot_v3.py
```

输出必须为 `"valid": true`，并且三路 video frames 均等于 data frames。数据列
`observation.state` 和 `action` 都是 27D：14 个双臂关节、3 个头部关节、5 个躯干
关节、左右 OmniPicker 单主动轴，以及底盘 `linear.x/linear.y/angular.z`；三路视频键为
`observation.images.base_0_rgb`、`left_wrist_0_rgb`、`right_wrist_0_rgb`。
v1.3.8 数据集还必须包含 `source.capture_monotonic_ns`、
`source.camera_timestamp_ns`、`source.camera_integrity_timestamp_ns`、
`source.camera_arrival_timestamp_ns`、
`source.state_max_age_ns` 和 `source.action_max_age_ns`。旧 20 fps 数据只能用
`--legacy-compatible` 单独审计，不能追加到 v1.3.8 的 30 Hz 数据目录。

相机排障及静止录制验收（先停止遥操/录制器）：

```bash
source scripts/env.sh
.venv/bin/python scripts/probe_camera_integrity.py --seconds 10
.venv/bin/python scripts/verify_stationary_capture.py --seconds 10
```

验证脚本在临时目录录制、保存并审计，退出后清理测试数据；不会写入 `mocap_data`。
成功时输出 `STATIONARY_CAPTURE_AUDIT` 与 `valid: true`。若相机无输出或时间检查
失败，先按日志恢复对应上游；详细验证边界见上面的 v1.3.8 报告。

所有平滑参数在 `config/control.json`。一次只改一类参数，每次修改后重新运行
单元测试、离线 benchmark 和 Shadow；任何配置改动都会使旧的实机验收失效。

| 参数 | 默认 | 调整影响 |
| --- | ---: | --- |

| `target_cutoff_hz` | 5.0 Hz | 越低越平滑但延迟越大 |
| `joint_deadband_deg` | 0.03° | 越大越抗微抖，但可能吞掉微小输入 |

| `chassis.yaw_position_scale` | 1.0 | 人体与底盘目标转角比例 |
| `chassis.position_gain_s_inv` | 1.8 | 平移位置误差的追赶强度 |
| `chassis.yaw_position_gain_s_inv` | 2.2 | yaw 角度误差的追赶强度 |

| `torso_pitch.a_hold_s` | 0.35 s | A 单独按住多久后启用俯仰；A 不再承担录制功能 |

| `recording.double_click_s` | 0.35 s | 双击最大判定窗口；X/Y 没有最小点击间隔 |

修改 `command_hz` 时必须同步修改 `collision_check_hz`。不要绕过
CollisionGuard、反馈超时、一次性授权或 Ruckig 轨迹约束来追求“更灵敏”。
