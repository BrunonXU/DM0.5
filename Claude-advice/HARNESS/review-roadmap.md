# F1 Harness 改造计划（给人看的总览）

- 基线：代码 `750ca46`；本计划在 [review.md](review.md)（H-01 至 H-19）之上，增加架构层面的改造和统一的验收指标。
- 配套文档：[核心架构与模块职责](review-architecture.md)、[验收指标与执行细节](review-acceptance.md)（Codex 必读）、[交给 Codex 的开工指令](review-handoff.md)。
- 状态：用户已于 2026-11-24 确认本计划和 R-1 至 R-5（见文末）。review.md 中带 `[!]` 的条目仍须逐项确认；阈值在基线出来后可由用户调整。

**一句话结论：先定指标，再改架构。** 过去 40 多版没有一次完整成功，不是因为缺功能，而是因为每一版的“完成”都用测试通过数、回放通过来定义，没有一版用“真机上走到了第几步、成功了几次”来定义。所以这份计划把评测体系排在第一位，并规定：**任何改动的验收只认真机漏斗指标，软件测试只是上真机的门票。**

**架构上做三件大事：** 安全检查收敛成一个小内核，其余环节改为“尽力执行”；把“探索开发”和“部署执行”拆成两个模式，部署时跑冻结程序、不调用大模型；接触阶段（对准、插入、判抓）改为闭环。感知和规划组件的替换排在后面，先用现有组件把流程跑通。

**关于数据可见性：** 写这份计划时，仓库里没有任何历史运行数据，现状基线未知。因此第一项任务是量基线，并且规定 Codex 把基线数据和每次真机测试报告上传到 GitHub 的 [evidence 目录](evidence/README.md)；没有上传的结果，审阅时视为不存在。

## 里程碑（真机结果，按顺序达成）

| 里程碑 | 定义 | 通过标准 |
|---|---|---|
| M0 流程打通 | 立放方块，任一布局 | 出现第 1 次无人工介入的完整成功（放置验证成功且有控制端放置回执） |
| M1 基本可靠 | 10 个固定立放布局，各 1 次 | 自主成功 ≥ 8/10；不调用模型的首动时间中位数 ≤ 10 秒 |
| M2 见过场景快速路径 | 同 10 个布局，跑冻结程序 | 模型调用 0 次；成功 ≥ 9/10；开始到放置验证的中位数 ≤ 30 秒（M2a），再到 ≤ 20 秒（M2b） |
| M3 姿态泛化 | 10 个横躺或倾斜布局 | 自主成功 ≥ 7/10 |
| M4 正式验收 | 20 个冻结的留出场景 | 自主成功 ≥ 18/20（沿用现有 `evaluation.py` 的口径） |
| M5 形状迁移 | 换一种新形状 | 开发投入 ≤ 4 小时真机时间；10 个布局成功 ≥ 8/10 |

样本量说明：10 次试验统计上很粗（8/10 的 95% 置信区间大约是 44%–97%），只用来决定“能不能进下一阶段”。对外报告的数字以 M4 的 20 场景为准。

## 核心改动（按优先级）

### A. 指标与评测体系（最先做）

- **为什么**：没有统一指标，Codex 会用“测试通过数”代替目标，并为了让测试通过不断加检查。
- **论文支撑**：PyRUA-REAL、ACE-CaP-0 都用“冻结程序 × 固定次数真机试验的成功率和耗时”作为唯一结果指标；ACE-CaP-0 每个任务固定 30 次试验。
- **做什么**：
  1. 写一个漏斗统计脚本，从现有运行记录算出每次运行走到了哪一步、在哪一步因为什么原因停下；
  2. 先对历史运行跑一遍，得到现状基线；
  3. 固定 10 个立放布局和 10 个横躺/倾斜布局；
  4. 规定每个 PR 必须附带指标报告。
- **预期效果**：第一次能回答“卡在哪一步、占多大比例”；后面每项改动都有前后对比。
- **验收**：脚本能在全部历史运行上产出漏斗表；基线报告写进 `HARNESS/agent/experiments/`。

### B. 安全内核收敛，其余尽力执行

- **为什么**：身份、哈希、新鲜度在五层重复检查，任何意外组合都导致零发布或撤权。
- **论文支撑**：PyRUA-REAL 报告，每次上机前多一道审查，两次试验的间隔中位数从 3.4 分钟变成 16.9 分钟。ASPIRE 把“真机安全探索”列为未解问题，说明安全应该是一个独立、清晰的部件，而不是散在各层。
- **做什么**：执行 H-01、H-02、H-03（可直接做），H-05（待确认）；并立一条规矩：硬保护只有 6 类，其余检查的失败一律不得阻止动作，只能触发“用最新测量重扫”或告警。每个 PR 报告“新增拒绝原因的数量”，必须为 0，除非属于 6 类硬保护。
- **预期效果**：非物理原因的零发布拒绝大幅减少；达到 M0。
- **验收**：非物理拒绝 ≤ 每次运行 1 次（以 A 的基线为参照，至少减半）；10 次试验中“因非物理原因终止”的 ≤ 1 次。

### C. 开发/部署双模式

- **为什么**：现在部署时让 Astra 在线决策，每轮 13–30 秒；而经验晋升又几乎不可能。
- **论文支撑**：PyRUA-REAL 中，在线调模型比冻结程序慢 4.6–5 倍；8 个真机任务平均成功 91.1%。ACE-CaP-0 的冻结程序 240 次试验成功 92.1%，并显示“卡住时请求一次示教”比只给文字指导好（86.7% 对 60%）。
- **做什么**：
  1. 部署模式：网页开放“程序优先”（H-16），先跑冻结程序，失败再交给 Astra；
  2. 开发模式：编码 agent 在真机上“试一次、看记录、改程序”循环，产出冻结程序；可以请求人示教；
  3. 开发档的经验晋升放宽（H-12）。
- **预期效果**：见过的场景 0 次模型调用；达到 M2a。
- **验收**：M2 的三个数字；开发模式下两次试验的间隔中位数 ≤ 5 分钟。

### D. 接触阶段闭环（判抓、对准、插入）

- **为什么**：对准是一次性开环路点；判抓在夹爪遮挡时缺图像证据；左腕补孔依赖头部深度，持块后容易被挡。
- **论文支撑**：PyRUA-REAL 的网线插入用纯脚本 0/4 成功，汉诺塔靠“粗定位加腕部相机反馈”才完成；ACE-CaP-0 的充电头插入 30/30。RoboDuo、Recova 把学习策略当作程序可调用的原子技能。
- **做什么**：H-15（夹爪为主判抓）、H-07（闭环对准）；左腕改为手眼标定后自己测孔；可选：把 π0.5 或 RLT 接成“最后几厘米”的原子技能。
- **预期效果**：对准和插入阶段的到达率明显提高；达到 M1。
- **验收**：抓取判定的误判 ≤ 1/20；到达对准阶段的试验中，插入成功 ≥ 8/10。

### E. 规划提速

- **为什么**：运输只有 4 个模板，终点是单个精确位姿；抓稳后串行规划 5–7 秒加复核 2.6–4.5 秒。
- **论文支撑**：cuRoboV2（GPU 上做逆解、避碰和带动力学约束的轨迹优化，并能从深度图直接建距离场）。
- **做什么**：H-04、H-06、H-17。用 cuRoboV2 替换“模板加 OMPL”的评估暂缓（用户决定，见文末 R-5）。
- **预期效果**：运输候选耗尽的情况基本消失；达到 M2b。
- **验收**：运输规划失败 ≤ 1/20；抓稳到运输首动 ≤ 1.5 秒。

### F. 感知升级（横躺、新形状）

- **为什么**：位姿估计默认积木立着、能看到矩形面；形状写死为方块。
- **论文支撑**：FoundationPose 系列和 Point2Pose（基于模型的 6D 跟踪，遮挡后能恢复）。
- **做什么**：H-08、H-09、H-14。基于 CAD 的 6D 位姿跟踪的评估暂缓（见文末 R-5）。
- **预期效果**：达到 M3，为 M5 做好准备。
- **验收**：横躺/倾斜布局位姿可用率 ≥ 9/10；M3。

### G. 经验与 RSI

- **为什么**：经验只进提示词，不改变排序和参数；检索按完整指令精确匹配。
- **论文支撑**：ASPIRE 的技能库存“失败特征 → 适用条件 → 修法”，而不是整段程序；PyRUA-REAL 中带原子技能库做新任务，成功率从 21.3% 提到 40.0%。
- **做什么**：H-10、H-11；经验条目改为修复知识格式；按场景类别统计各参数的成功率并自动选用。
- **预期效果**：同类失败第二次出现时不再需要 Astra。
- **验收**：重复出现的失败类型中，第二次起由本地处理的比例 ≥ 70%。

### H. 任务迁移阶梯（更大的目标）

立放方块 → 横躺和倾斜 → 同一个桶的三角和圆 → 多块有遮挡的整桶分拣 → 叠放等新任务。对外的定位是“F1 上安全的真机自我改进”：安全内核、发布账本和证据留存是现有工程的强项，正好对应 ASPIRE 列出的真机未解问题。每上一级台阶都按 M5 的口径报告：投入多少真机时间、成功率多少、复用了多少已有技能。
