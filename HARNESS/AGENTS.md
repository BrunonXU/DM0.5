### [CLAUDE_ADVICE] 审阅建议的执行（2026-11-24用户确认）

[Claude-advice/HARNESS/review.md](../Claude-advice/HARNESS/review.md) 是 Claude 对 HARNESS 的只读审阅和改进执行规格：前半部分给人看，后半部分给 Codex 逐条执行。分工原则、状态标记、执行顺序、遇 `[!]` 停下询问以及回写格式，统一以 [Claude-advice 说明](../Claude-advice/README.md#codex-执行与回写约定) 为准，本节不重复。下面只写 HARNESS 专属规则。

1. **开工前必读。** Codex 每次在 HARNESS 开工，先读该 review 的状态，再读本页和 STATUS。
2. **本轮做什么。** 用户没有另行指定本轮任务时，按 review 的优先级处理条目。用户当轮明确指定了别的任务时，先做用户的任务，review 条目顺延，不得夹带执行。
3. **冲突时以谁为准。** 依次为：用户当轮明确指令 > 本页及 [故障分级](docs/FAULT_POLICY.md) 中的硬保护和发布验收规则 > review 条目 > 其他文档的旧描述。review 与本页冲突时，按本页执行，并把该条目改为 `[!]`，写明冲突点。
4. **执行范围。** 只改条目列出的文件和行为，不顺手重构、不扩大范围。不改 DAgger、F1-4242、RLinf 和 `third_party/` 上游源码；需要改这些工程的条目另开任务，并先读对应的局部规则。
5. **硬保护不得移除。** 本清单是 review 执行时的权威，review 只引用它的代码位置。以下保护无论 review 怎么写都保持不变：
   - 授权与会话身份；
   - 实时反馈新鲜度与失联撤权；
   - 原生关节限位、自碰撞、环境碰撞，以及对实际路径的扫掠；
   - 已发布、部分发布或发布状态未知时不重放，零发布须由 owner 证明；
   - 相机内参、标定和时钟域身份；
   - 原始记录写盘失败即停止。

   放宽其他检查时，必须在提交说明中写明它对应的物理失效、适用阶段、故障等级和恢复方式，与上文“实现与执行边界”的要求一致。
6. **完成后的 HARNESS 额外回写。** 按 README 回写 review 状态之外，涉及部署或真机结论时，还要按本页规则更新 STATUS 和 TODO。
7. **验收不降级。** review 中的验收标准是最低要求；发布前仍须完成本页“每次发布前的全流程零输出验收”。

## 每轮接续

0. Codex 先按上节读取 [Claude 审阅与执行规格](../Claude-advice/HARNESS/review.md)，确认本轮要执行的条目和待人工确认项。
1. 核对 STATUS 页首的当前目标、已确认决定、实际完成范围、未验收项和下一步，现场操作前复查实时状态。以最新用户指令与对应证据接续工作。
2. 设计改动按上方章节核对依据，依赖选型与源码来源查[上游复用清单](docs/UPSTREAM_REUSE.md)。按本轮问题选读实验与代码。
3. 涉及 F1 积木时，先读其 [AGENTS](../tasks/F1_ComplexyToys/AGENTS.md)与 [STATUS](../tasks/F1_ComplexyToys/STATUS.md)。修改 DAgger、RLinf、F1-4242 或其他工程前，再读对应局部规则；HARNESS 不另维护 F1 当前状态。
4. 结束前核对对应正文、STATUS、TODO 与证据链接，只更新发生变化的内容。未完成时留下已做、未验收、阻塞与可继续执行的下一步。
5. 并行工作只修改约定文件，合并前重读最新内容；保留他人的未提交改动，不擅自提交、推送或覆盖历史证据。

## 代码与实验归属

改动前先找到正式入口、现有实现和调用它的测试。遇到同类失败，先用原请求或固定输入复现，再决定是改现有合同、补一个回归样本，还是开展新的实验。按职责落在以下位置。

| 要交付的东西 | 放在哪里，怎样接回项目 |
|---|---|
| 跨入口复用的行为 | `src/f1_harness/` 中负责该能力的模块。网页、CLI、回放和预热通过包内接口复用逻辑。保留已有参数、错误、取消及重试语义；调整模块时核对打包清单和旧调用者。 |
| 可反复运行的命令 | 先扩展已有 CLI 或 `scripts/` 下对应命令。入口负责参数、调用和输出，共用实现留在包内。有独立用途才增加脚本，以操作命名；版本、场景和运行编号作为输入。维护入口见[开发导航](README.md#源码与配置)。 |
| 平台实现与配置 | 机器人端入口放 `native/`，感知环境及依赖锁归 `perception/`，共享示例和依赖身份归 `configs/`。跨工程能力由原所属项目维护。 |
| 回归与现场样本 | 复用 `tests/` 的对应套件。小型可分发样本放 `tests/fixtures/`，记录来源和预期；真实大输入留在原处，验收清单记路径、内容哈希和使用它的用例。报告中分别列出通过、缺输入和环境限定跳过。 |
| 一次实验或临时探针 | 按[实验索引的记录规则](agent/experiments/README.md#记录规则)找到同一问题的复盘。一次性驱动、配置快照和机器输出归该实验的 `artifacts/` 子目录；第二个独立调用者出现时，核对既有脚本后再提取共用部分。 |
| 现场原件、经验与发布 | `runs/` 保存逐次运行原件，`experience/` 保存实际学习数据，`releases/registry.json` 维护框架身份。冻结包、回放输入和验收回执保持登记的路径与内容身份。空间整理须先查消费者、登记和恢复方法，按原件、可再生成输出分别处置。 |

## 实现与执行边界

- 优先复用已固定身份的上游源码与现有 F1 能力；先查现成接口，再做任务适配，不复制一套通用模型、机器人或控制框架。
- 项目初始接入默认只读与离线。日志、保存观测、几何计算及接口模拟通过，不代表控制网关、模型调用、标定或硬件动作已经实现。
- 真实运动继续由实际控制所有者负责授权、锁、通信与保护。2026-11-05用户明确改为 infra 点击开始／停止，不需要手柄或终端 Enter；网页开始绑定本次任务与运行，由独立 Harness web owner 消费，不伪造 F710 包或物理 START。纯读取、辅助服务启动和刷新不能授权运动；旧手柄入口仍独立保留，不复用旧授权或绕开原控制保护。
- 模型输出是待校验的计划或建议；不能直接冒充可信硬件状态、成功判据或已执行动作。执行与反馈分别留证，失败、保持、取消和恢复不得合并成成功。
- 故障按[故障分级与有界恢复](docs/FAULT_POLICY.md)处理：实际限位／碰撞、反馈失联、未知或部分发布及原件记录故障保留原硬保护；候选不可达应改变路径后重新校验，不能绕过执行检查。只有 owner 证明零发布且满足明确时效条件的请求才允许有界重规划，不能把反馈恢复解释为自动重新授权。
- 测试验收、性能诊断或派生产物阈值不得直接成为动作的一票否决项。新增运行门槛必须注明对应物理失效、适用阶段、故障等级、证据与恢复方式；耗时预算不替代通信 watchdog、反馈新鲜度和原限速。已接受的粗标定开发身份按其合同执行，不重新引入未约定的精密认证门槛。
- 修改网页 owner、授权或故障恢复时，除 HARNESS 自身回归，还运行 `scripts/check_native_integration.py`。它使用真实 DAgger ControlLoop、owner、WebHarness 与任务引擎，传输为假实现、不启动 ROS 或机器人动作；单独的 HARNESS pytest 不覆盖这段跨工程生命周期。至少覆盖无手柄授权、发布前静止时序等待、反馈失联撤权、未知／已发布不重放和停止处理，真实动作验收另外记录。
- 修改参考速度、连续路点或转腕时序时，原生参考路径通过与程序返回成功不足以证明方案可用。对受测配方审计实际F1Owner/Ruckig输出的环境扫掠、发布完整性和原限速，绑定控制profile与场景身份；输出检查失败的方案不得作为已验证提速或部署配方。此为由真实代码反例支持的配方验收，不把诊断耗时另加为运动中断门槛；现场profile和物理误差仍需单列验证。
- F1 RLT 可沿原任务并行推进，资源、数据准入、训练身份和部署状态仍以原任务为权威。HARNESS 的阶段推进不隐含切换模型、启动训练或替换生产控制。
- 每次训练包括预检与恢复都遵循根规则接入 W&B，分类和 run 身份明确；没有发生训练时，不创建虚假的训练结果或在线监控结论。

## 每次发布前的全流程零输出验收（2026-11-10 用户明确要求）

每次新增功能或修复后发布，必须先使用保存的真实运行数据，沿正式入口、实际状态合同与工具接口走一遍完整流程。不能让用户反复在真机点击开始，替开发者发现启动、字段、工具接线或生命周期错误；单元测试计数、服务健康和文件哈希不能代替这项验收。

优先采用历史数据回放；必要时可将候选部署到实际运行环境验收，但最终动作发布器必须替换为只记录、不向硬件输出的接收端。这里的 shadow 指端到端零输出验收，不要求操作者先跑一次网页 shadow，也不允许用正式机器人动作来完成发布自检。

- 使用真实生产组件生成授权／状态返回，覆盖准备、授权、初始缺几何、看图与提示、感知更新、规划、技能提交／结果、正常完整技能链及停止收尾；至少保留最近实际失败记录作为回归输入。不得由 mock 补造生产接口不存在的字段。
- 同时覆盖已知成功场景与本次失败／恢复分支。记录候选命令、实际消费和下一阶段推进；确认命令能到达零输出接收端，不能仅以 Python 程序返回或 IK 可解判定全流程通过。
- 共同合同改动须做跨层对照：同帧仅改变待执行请求、同目标仅增加诊断或恢复无关测量、不同请求完成同名技能、程序中段内部重试，不能悄悄改变物理状态、可执行性、进展或经验归属。按全部受影响技能和正常／恢复／补验组合验收；实际新障碍、附件变化和撤权仍按当前证据重验。这是发布验收要求，不新增运行门槛。
- **新增观测字段必须走正式通信验收。** 使用实际完整窗口和最大常见组合经过请求、反向proof、HTTP及日志收集，不以组件单测或绕过RPC的直接方法调用代替；完整证据不能因传输缩减而丢失，历史哈希兼容与当前引用恢复分别验证。此为发布检查，不新增运行准入门槛。
- 模型、相机、反馈或执行结果若被回放／模拟，逐项标注。回放成功不等于真机成功，替代模型响应不能冒充实际 Astra 调用，预录成功反馈不能证明新候选动作在物理世界有效。
- 涉及感知接线、模型部署或时序时，使用连续真实RGB-D及对应反馈跑正式感知组件和实际分割模型，在目标计算环境验证场景能够持续被下游消费，并分别记录实际帧年龄、连续证据和质量告警；不能把性能预算重新当作运行准入。不得用单张分割耗时、RGB视频、保存的几何或不带实时节奏的动作回放替代。缺少连续深度记录时先零输出只读采集，不重写旧帧时间来伪造新鲜样本。用户当轮明确要求停止测试、直接部署时优先照办，并如实登记未执行的验收，不补写通过。
- 验收运行必须有独立身份，绑定代码／配置／数据来源，保存 trace、动作接收记录与零硬件输出证据；故障后不得重新发送未知状态的动作。保留正常限位、碰撞、反馈和授权合同，不为跑通回放放宽正式控制。
- 发布回执分别说明“全流程回放通过”“部署核验通过”“真机待验”；若数据不足或某环节未贯通，明确缺口，不称为可直接真机完整运行。源码冻结后才形成最终回执；修改影响链路时重跑受影响的完整路径。

现有入口为 [真实接口启动回归](tests/test_real_bootstrap_contract.py)、[历史场景完整动作回放](scripts/replay_full_owner.py)（选择 `approved-output` 接收真实 F1Owner/Ruckig 输出）及[实际输出审计](scripts/audit_replay_output.py)。回放驱动必须跟随生产调用合同维护，不能因驱动漏传参数而修改正式执行判据。这是开发发布验收，不是在真机任务中新增中断条件。

## 私密配置与源码身份

- 根 `API.MD` 是已有本地私密文件。凭据只能由已授权调用所需的本地认证组件读取；正文与取值不得进入终端输出、日志、模型上下文、网页、导出包或 Git。文档仅记录配置来源和可用性，不记录秘密值。
- 认证字段与业务输入分开，必要诊断只输出脱敏结果；不得为检索、摘要或说明将凭据文件发送给模型。
- 上游独立检出保持各自 Git 身份，忽略的源码目录由锁定清单索引来源、提交和适配关系。不要把嵌套 Git 目录误加入根仓库，也不关闭稀疏检出或改现有上游远端。
- 保留源码、配置、数据与运行身份的对应关系。对人的框架版本按“产品／技术＋V整数”独立登记，先核对发布登记与已预留编号；未分配时写未分配，不猜测 V1，也不套用 F1 控制版本号。
