## 后续方向：减少完整任务的模型往返

用户要求按五轮任务的总模型耗时优化，不采用字符级压缩。JSON字符串外空白不影响JSON解析值，但模型行为不能据此承诺完全不变；该实验不再作为接线候选。本轮方向澄清没有新调用API或更改线上逻辑。

当前已部署V1（`d9d8b5efa52a`）包含首轮证据包、多实体同cell提示、`inspect_plan`、`pick_with_candidates`、完整抓放程序和owner自动收尾。重点是通过真实场景检查模型是否稳定消费已有能力，定位为何仍返回模型：观察提示与实际几何间的决策可能必要，逐个问候选、正常阶段确认及完成后写finish通常可以由现有程序处理。

目标结构为：首轮一次定位当前可见实体并请求真实几何；第二轮据实测结果选择连续参数候选／有界完整程序；本地依次预览、执行、验证和恢复，全部完成由owner结束。只有新障碍、未覆盖失败、证据歧义等需要新判断时回到Astra。计划、碰撞、抓持和放置检查仍逐步发生；五轮变两轮属于条件满足时的架构目标，未宣称V1实测已达成。

固定前缀的生产接法：服务准备时按知识／工具版本构建稳定规则和工具说明，在相同模型设置下预热并设置显式断点；任务与每轮新增测量、图像、失败证据排在后面。每个任务保持独立状态，已发送历史只追加，不逐轮重写。规则／工具版本变化时更新前缀身份；未命中缓存仍正常推理，不增加机器人运行门槛。现有HTTP方式仍发送完整前缀，提供方复用计算，不是把文本只发一次后永不发送；预热耗时与费用单列。当前实验尚未测试变化snapshot的跨任务缓存。[官方缓存机制](https://developers.openai.com/api/docs/guides/prompt-caching)。

如果五轮确实都依赖上一轮的新事实，应保留这些决策边界，优化历史／推理项完整续接和请求链路；不能把互相依赖的动作并行执行或以预算截断必要判断。现有planner已经追加完整`output`与工具结果，持久会话本身不构成新增五倍提速机制。未来经验复用继续按用户先前决定，放在完整流程稳定后；优先复用物体相对程序与适用条件，每次重新测量。[减少请求的官方建议](https://developers.openai.com/api/docs/guides/latency-optimization)、[保持历史前缀](https://developers.openai.com/api/docs/guides/preserved-reasoning)。
