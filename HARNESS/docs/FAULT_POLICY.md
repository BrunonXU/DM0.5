# HARNESS：故障分级与有界恢复

**普通缺测量、单条候选失败及动作后缺证据应按当前阶段恢复，不能误报整个任务物理无解。** 局部推进、支撑释放和程序复用遵守同一owner合同；本页规定处理边界，具体冻结、部署及现场结果以[STATUS](../agent/STATUS.md)为准。

粗任务中视觉处理超出500ms预算、连续静止历史不足及允许的接收时间配对保留质量告警，不在后续层重复成为精度硬门槛。真实缺目标、实测仍运动、反馈失联、身份错误及限位／碰撞分别处理；原始时间不改写，动作前图像不能充当动作后成功证据。下文日期段落保留历史合同，旧精密模式的时限不能重新套回当前粗任务。

**只有当前动作所需的物理条件、数据身份和执行权限才决定动作能否继续。** 限位、碰撞、真实反馈失联、未知发布状态及原件记录故障必须阻止后续动作；尚未发布的过期候选、临时缺帧和性能诊断分别处理，不能把所有异常都变成整项任务失败。

### 普通预览失败与局部推进

`preview`／`inspect_plan`中的缺实体、部分场景及已识别观测缺失返回`planned=false`、具体原因、当前作用域和零发布信息。观测等待只消费原有获取预算，数值规划耗时不计成观测获取失败；身份、授权、反馈和连接错误仍独立处理，不包装为可随意重试的视觉问题。没有取得当前观测时，不补造对象、场景ID或测量时间。

`pick_with_candidates`与`move_and_reobserve`共享同样的列表内恢复语义：因场景缺失受阻时，刷新同一候选一次；持续缺测返回场景不可用，不把其余候选假记为几何失败。几何候选被拒可以继续不同方案；已提交后仅凭原owner明确的终态零发布数值拒绝才换候选。部分／未知发布、停止或控制故障不重放；动作已成功但下一次观测失败时，保留运动回执和当前位置，从补观测继续。

头部重复源时间戳或非递增序号可保留同一任务／采集／标定作用域内、此前独立测得的静态桶体姿态。该值标为`retained_static_fixture`并保留原始时间与证据，不生成精确孔口，也不冒充当前测量。当前腕部证据仍须匹配；换任务／epoch／标定、矛盾新测量或其他失效会清理相应记忆。复核只允许明确的静态记忆来源解释相机集合变化，不能把身份变化一并放过。

接近候选先尝试同抓姿的直接连接，再尝试历史示教路线；默认以当前关节姿态作为数值求解参考，显式登记的冗余偏好仍按原合同执行。预抓端点与目标粗包络重叠时，可按已有分离诊断修正中间接近点，最终抓点／抓姿不变，并重新检查整段与后续抓取。未证明通过的粗扫掠不写成原生碰撞或物理不可达；两条路线的失败保留在原候选诊断中。

owner确认零发布的数值拒绝返回当前数值几何摘要，减少只为查询状态而新增的一轮模型交互。附加查询失败不覆盖原动作回执，也不重放动作；未知／部分发布继续按原合同处理。局部深度原件存入当前运行已有证据库，IPC携同源内容引用，规划端恢复并核验完整证据；引用本身不授权运动，LLM摘要不携深度载荷或内部引用。

### 支撑接近与松爪

`move_tcp(..., support_contact=True)`用已测附件和登记桌面／物体包络检查接近支撑面。它反向复用原离面单调证明，保留工具与其他障碍检查；接触带内纯横移、超出既有接触误差容差的穿透、旋转途中下穿均拒绝。接触容差是模型误差合同，不是新的力觉测量或零物理误差承诺；不替Astra选择扶正方向、距离或路线。

`release_supported`只在当前持物与静止证据、支撑接触候选成立时规划张爪，实际数值目标与新场景复核都要求手臂保持、仅夹爪变化。动作完成后等待新RGB-D中的未持物、静止且接近支撑面的证据；缺证据只返回原请求的验证checkpoint，不重复张爪。补验成功清理旧抓持／插入阶段、抓姿选择和旧运动续跑凭据，不重置真实重抓／纠偏额度，也不把此结果记成已插入或已完成任务。

支撑测量报告原始帧、标定与坐标、支撑面来源、间距及对象三轴与法线夹角。当前粗任务允许的`receipt_only`仍带源时间未验证告警，不另加精密时钟门槛；错误帧／身份不能降级为有效证据。`support_observed`表示当前未持物静止对象与登记支撑几何一致，不是承重力证明。姿态角尚未接成独立的“扶正成功”判据，自主扶正没有真机成功记录。

已完成接近的粗任务可以保留同对象、带原观测来源的起始支撑关系：前一测量须处于原支撑接触带，新旧物体角点变化须满足既有接近复核合同。新测量的物体与桌面均不移动；仅离面检查记录固定的当前接触基线，仍证明不继续深入且终点离开支撑面。工具／桌面、桶体、原生碰撞与运动限值保持。此规则解决跨视图粗测量造成的起点误拒，不适用于无来源的任意穿透，也不构成承重或已抓稳证据。

## 空爪重抓的目标接触退出（2026-11-09，源码已实现、未部署）

每个工具盒必须从初始最近的接触面向外移动；逐段平移须覆盖旋转导致角点靠近的上界，且退出终点重新满足完整工具净空。原数值解的实际FK路径和新场景复核分别验证；若不成立，返回具体`actual_IK_target_departure_not_proven`或`revalidation_target_departure_not_proven`。张爪阶段只允许夹爪变化，不能借该操作在接触区内移动关节。

跨相机跨度与单路几何配对不同：当前场景对各路 RGB-D 分别检查有效性，并匹配真实反馈历史；在所需静止条件、坐标链和新鲜度全部成立时，头部与腕部图像之间的跨度记录为诊断。它不豁免单路错帧、错误深度、缺失反馈、源时钟异常或移动场景的时序要求。

头相机明确的临时缺帧／重复或倒退源时间戳不再清除已经独立验证的右腕停稳、跟随和持物历史，可输出仅含右腕物体的场景，支持抓持验证／在手检查／重新观察。V25的部分场景全运动拒绝属于历史实现；后续开发源按本页的当前阶段、静态桶体记忆及独立路径证据处理。缺少路径障碍时仍不允许直接运动；源时间倒退本身不满足静态桶体记忆保留条件。右腕历史使用原始采集时间与原间隔上限，标定、时钟、头身参考或右腕数据异常分别处理，不能把任意错误都归为头部缺帧。

粗标定开发许可只对应已登记的 `development_coarse` 档案及来源，不免除标定身份、坐标变换和动作检查。视频、索引等派生记录失败与原始执行记录失败分开：原件写入失败必须阻止后续动作；派生失败不能把已有原件改称写盘失败，也不能据此宣布验证成功。

## 零发布候选重规划的具体边界

当前 owner 为以下明确登记的纯时效原因，以及核对安全锚点、原始绑定与零发布后的 `owner_candidate_rejected`，签发 `no_motion=true`、`retryable=true` 的终态失败：

- `planning_observation_expired_before_publication`；
- `planning_frame_expired_before_publication`；
- `planning_state_expired_before_publication`；
- `revalidation_proof_rejected:revalidation_proof_expired`；
- `plan_revalidation_rejected:revalidation_measurements_expired`；
- `numerical_plan_rejected:planning_measurements_expired`。

`planning_state_expired_before_publication` 指**原观测中绑定的状态快照**过期，不是实时反馈失联。执行前必须另外确认当前反馈新鲜、完整关节／保持参考未改变、当前请求与观测／标定绑定有效、授权仍有效且未请求保持。owner 的发布账本中不能出现这个请求的任何发布。

重新验证使用专门的 `RevalidationExpired` 类型区分纯过期与其他失败，不能看到错误字符串包含 expired 就重试。判断时间年龄前，先检查请求／会话／epoch、候选与观测内容哈希、相机／标定／配对身份、阶段目标和几何，并核对当前 live scene 的物块、孔口及在手关系在登记容差内一致。身份不一致、几何不一致或非法时钟与过期同时发生时，仍按前者拒绝，不归为纯时效。

live scene 暂时为空时，只允许 `scene_expired`、`perception_latency_exceeds_observation_budget`、`evidence_archive_exceeds_observation_budget`、`verification_transport_exceeds_observation_budget` 四个明确的纯时效原因进入等待。原候选不获得发布资格；取得新场景后，worker 对**同一候选**重新执行 FK 路径与环境扫掠，原技能截止时间和会话租约不续期。过期 worker 结果返回时若已有更新场景，也优先重扫同一候选。其他 live scene 失效原因不能借此等待分支恢复。

FK、场景重建和几何扫掠均在 worker 执行。owner 实时路径只检查绑定、廉价一致性、时间和真实反馈，不在控制循环里补做 FK 或联网等待。

runner为已登记的接近、抓持／重抓、转移、对准、插入、释放和撤离技能最多追加**2次零发布重规划**。每次换新观测及请求ID，保持同一owner、会话、任务和epoch；原请求仍是失败回执。恢复该未执行尝试占用的语义计数，不消耗真实重抓／纠偏额度。重试同时共用首次提交后的技能期限及整个任务期限，不逐次续期。

已经发布、部分／未知发布、取消、当前反馈过期、关节参考改变、标定／授权／相机身份变化、证明内容不匹配不走该恢复路径。只有明确登记的场景变化类拒绝可废弃候选后重算；不能把任意异常转为可重试。提交回执丢失先查原请求，查不清保留未知并停止。最后一次发布前复核即使保留任务授权，也必须同步清掉此前已批准的排队目标，不能漏发旧动作。

方块姿态选择最近的四重对称坐标分支，并同步变换在手坐标；复核保留原观测哈希、重新生成阶段目标及检查实际FK路径。场景位置容差仍为配置的2mm；空中接近／转移／撤离终点另显式配置15mm粗定位容差，受已有15mm工具规划余量及净空约束，完整实际工具／夹持物扫掠不变。抓持和孔口接合不使用此粗终点容差；对准／插入／释放的位置预算仍受剩余孔隙限制。这是终点误差范围，不是动作长度限制，也不是已认证机械精度。

STOP按稳定的本次run／owner／task／准备会话身份受理，允许穿过该任务的撤权与finish／close，不放宽START的当前epoch要求。网页先记录owner实测停稳回执，再结束planner和关闭会话；清理回执失败单列告警，不抹掉已收到的停稳证据。没有真实回执时仍保留未确认，不能靠进程退出伪造停止。

这里的 2 次是**执行前重规划预算**，与任务中最多 2 次局部修正、1 次重新抓取分别计数。任务级恢复仍须有真实技能结果与新的几何证据；软件支持恢复分支不等于真机已经完成恢复验收。

## 时间预算与硬保护分开

离线数值候选增加末端误差停滞判断：同一插值路点的位置或旋转误差，连续25次迭代都没有累计改善超过相应既有求解容差的0.1%，结束该候选的计算，返回原`bounded_IK_did_not_reach_goal`及`termination=cartesian_no_progress`。每个新路点重新计数；有累计改善则继续，不以关节仍在零空间移动代替末端进展。这是优化器的收敛策略，会提前放弃部分慢收敛搜索，不是新的运动到位／精度门槛，也不证明目标全局不可达。

这类失败仍走原候选换姿／换路径处理，不能触发重复发送已受理或未知状态的动作。原求解容差、限速、限位、碰撞、授权和owner输出校验保持。有限保存场景的判定一致不证明所有可行路径均不受影响；当前验证范围和未部署身份以STATUS为准。

网页静止HOLD的50ms时序波动按用户要求改为诊断，不再进入任务暂停或清空计算；日志保存原间隔和零发布证据，下一周期仍做全部正常检查。计算中的候选保留原观测时间、绑定和首次发布验证，不因这次告警获得新的有效期。真实反馈失联／目标失效仍撤销Harness epoch；未知或部分发布不能当作保持告警。

锁死故障下停止请求仍应被消费并记录，但已经关闭的发布端不能冒称保持已发布或实测已停稳。清理后允许在任务身份匹配、原件静止且控制锁可检查的条件下另行收集失败证据；收集成功不改变原运行的停止未确认和失败结论。

观测等待达到 **30秒** 记录警告并显示原因，不因此结束任务；完整任务的各项技能、规划、复核和恢复共用原 **300秒** 预算，不重置截止、不延长通信租约。原先转移90秒、其他运动30秒的独立截止已被替代。持续等待时记录路径点实测误差和剩余预算，观测等待仍维持心跳及权限检查。

runner从本次授权起共用**300秒任务预算**，观测等待、各技能与重试不会分别续期。预算在提交前耗尽，返回零提交的待处理结果；已接受技能仍受原owner截止时间及取消保持约束。停止RPC的收尾时间不代表允许继续运动，也不代表停止已确认。

动作后每轮验证等待最多**10秒**、RPC最多12秒。返回“暂缺新的动作后证据”时，只重新请求验证，不重新提交运动；沿用原动作后的时间下界与原技能截止时间。明确抓空、插入失败与无法判定分别处理，未确认插入不会松爪。已执行技能到期仍撤权保持，不伪装成零执行候选。

数值规划对接近、转移、对准枚举最多四个已注册方块对称候选，任一候选均重新执行几何、IK与路径检查；选择的姿态编号绑定重新验证，不能把另一姿态的证明套过来。数值候选耗尽返回待处理。owner首发前候选拒绝仅允许接近／转移新请求重算，并证明实测与保持姿态安全；有任何实际发布都不能套用。

这些是有界等待／任务截止时间，**不改变通信 watchdog、真实反馈新鲜度、动作有效期、关节速度、限位或碰撞保护**。等待期间不能把旧观测不断改时间戳；执行过程中不能因总预算尚有余量而继续使用失效反馈。

研发耗时目标、测试验收数值和性能告警不是自动的运动否决项。新增运行门槛必须同时说明它对应的物理失效、适用阶段、故障等级、所需证据和恢复动作；仅用于统计的数值应留在诊断或验收中。若确实影响当前运动条件，须将它明确落实为对应的数据或控制合同，而不是另加一个没有恢复定义的全局异常。

## 日志应怎样解释

每个失败至少保留请求／任务／epoch、发生阶段、原始原因、是否真实发布、授权变化及下一步处理。`retryable` 和 `no_motion` 来自 owner，模型或网页不能自行推断。暂停、保持请求、owner 已保持、实测停稳与任务成功分别记录；任务“异常结束”不应覆盖最初的拒绝原因。

使用[完整真机运行入口](DIRECT_ROLLOUT.md)查看该次运行的事件、owner 原件与 Harness trace。本页的恢复策略不能补造丢失证据；实际场景中未完成、待审和人工辅助结果继续分开统计。
