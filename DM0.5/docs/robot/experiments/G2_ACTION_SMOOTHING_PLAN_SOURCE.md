# G2 × DM0.5 动作平滑优化方案（历史设计与实验来源）

> 本文完整保留早期第一性解释、手部离线数据和方案演进。通用的当前原理入口为 [`../RTC_AND_CONTROL_TIMING_FIRST_PRINCIPLES.md`](../RTC_AND_CONTROL_TIMING_FIRST_PRINCIPLES.md)。

> 本文是方案讨论和实验设计，不是已经上机的功能，也不是现场操作手册。
> 当前真机基线仍以`00_G2_OPERATOR_GUIDE.md`为准。

更新日期：2026-08-05

## 1. 目标与当前边界

本阶段的目标不是单纯让机器人“看起来慢一点”，而是在不明显损失抓取、
放置和闭手时序的前提下，降低以下五种不同问题：

1. 首个chunk从静止目标突然接入模型动作；
2. 一个chunk结束后接入下一个chunk的位置、速度或加速度不连续；
3. 单个chunk内部的小幅高频波动；
4. 30Hz模型waypoint到双臂100Hz、双手5Hz硬件输出之间的频率差异；
5. Sync调度每个chunk结束后等待约0.47～0.52秒HTTP响应导致的停顿。

这五类问题不能用同一个EMA或同一个“平滑开关”解决。网络/推理停顿尤其不是
轨迹滤波问题；只改轨迹无法去掉0.5秒hold。

当前冻结基线：

- 75K checkpoint；
- Split硬件下发；
- 双臂前14D走30→100Hz `joint_servo_control`；
- O10双手后20D以5Hz走`move_ee_pos`；
- Sync是正式基线，Async暂不与平滑改动同时实验。

### 1.1 2026-08-04实测状态

已完成两轮60ms和一轮120ms cubic boundary blend真机采集。结果证明120ms确实
改善了chunk之间的接入，但没有消除chunk内部轨迹尖峰：

- 边界融合窗内双臂最大100Hz步进P95从约0.0126～0.0133rad降到0.0099rad，
  改善约21%～26%；
- 最新120ms运行的23个chunk中，13个chunk的最大步进发生在融合窗之后；
- 最新运行内部最大步进的主要尖峰来自右臂joint5，原始30Hz waypoint差约
  0.060～0.063rad，线性插值后仍形成约0.0188rad的100Hz步进；
- 因此120ms保留为当前实验基线，暂不继续加长；当前主要问题转为chunk内部，
  边界quintic minimum-jerk不再是紧接着要上机的唯一变量。

这里的结论不是“120ms解决了所有抖动”，而是它把边界问题压低后，使内部问题更
清楚地暴露出来。网络等待约0.5秒仍是独立的调度问题。

## 2. Telemetry是什么

Telemetry在本项目中指“运行遥测记录”。它不是控制算法，不会自动改动动作，
只是把模型、平滑器、安全门和硬件下发各阶段发生了什么记录到JSONL。

当前telemetry主要记录：

- 原始`50×34` action chunk；
- HTTP延迟和观测年龄；
- 原始chunk内的速度、加速度和jerk统计；
- 模型首点与measured state的距离；
- 限位裁剪、请求失败和safe hold原因。

第一阶段已实现的实际下发记录：

- `first_hand_command`：整次运行第一条被GDK确认成功的O10 20D命令及来源；
- `dispatch_summary`：每个chunk的双臂/双手发送数、相邻步进P50/P95/最大值；
- 最大变化关节、跨chunk第一条实际命令差和边界融合窗内最大步进；
- 每条已被GDK确认成功的5Hz手部20D命令、相对chunk时间和上一条跨chunk命令；
- 双臂100Hz和双手5Hz的实际发送间隔；
- 按各通道标称频率计算的命令轨迹速度、加速度和jerk。

2026-08-05进一步增加只读观测字段，不改变任何控制目标：

- 将34D首跳拆成双臂14D与双手20D各自的最大值和主导关节，避免手指大跳遮住
  双臂T1/T2统计；
- 每个chunk记录期望播放时长、理论100Hz发送数、实际发送覆盖率、有效发送频率、
  最大发送间隔以及超过1.5倍/2倍周期的间隔次数；
- 每个已确认成功的双臂命令记录维度范围、是否始终完整14D、是否全部finite；
- 120ms边界窗内记录实际发送数、最大步进，以及按真实发送时间计算的最大速度、
  加速度、jerk和主导关节；
- `runtime_start`明确记录边界曲线名称。正式默认仍为
  `cubic_smoothstep`，实验可显式切换为`quintic_smootherstep`。

2026-08-05 Sync延迟分段telemetry已加入，不改变请求合同和控制目标。每个
`action_chunk.request_timing_seconds`记录相机采集、34D状态读取、JPEG编码、请求载荷、
HTTP POST、响应JSON解析和50×34合同验证；升级后的7892服务还返回图片/表单解析、
输入transform、模型推理并回传CPU、反归一化以及响应构造耗时。客户端另外计算
`client_http_unattributed_seconds = HTTP POST - server handler`，近似表示上传、下载、
Flask框架和未归因等待。`run_summary.request_timing`给出各阶段P50/P95/mean，便于先用
Shadow定位瓶颈，再决定是否改模型或传输。

真实G2三相机10次Shadow（排除服务重启后的第1次冷请求）得到稳态端到端均值
约430.5ms：模型推理并回传CPU为306.2ms（71.1%），服务端multipart/PIL图片准备
55.4ms（12.9%），G2 JPEG编码21.0ms（4.9%），相机+state采集15.5ms（3.6%），
HTTP/Flask未归因15.2ms（3.5%），服务端输入transform 13.8ms（3.2%），其余JSON、
合同验证与输出小于1%。第1次冷请求约694ms。因此网络不是主要瓶颈；下一阶段先在
Shadow/离线评估`diffusion_steps`和模型执行优化，不能直接为降延迟牺牲动作质量。

记录只在原生硬件调用成功后进入统计；100Hz目标只在内存中汇总，每chunk写一条
JSONL，不在实时路径逐tick写盘。当前还没有rate limiter，因此“限幅命中次数和
限幅后跟踪误差”留到P2 rate limiter实现时增加。

## 3. Jerk与minimum-jerk是什么

Jerk不是一个滤波器名称，而是关节位置对时间的三阶导数：

```text
position q
  → velocity dq/dt
  → acceleration d²q/dt²
  → jerk d³q/dt³
```

位置连续但速度突变，或速度连续但加速度突变，仍可能让机械臂表现为“顿一下”。
Minimum-jerk trajectory是在起点、终点和时间已知时，尽量最小化整段jerk平方积分的
轨迹。

当起点和终点的速度、加速度都为0时，常用的五次多项式为：

```text
u = t / T
s(u) = 10u³ - 15u⁴ + 6u⁵
q(t) = q0 + (q1 - q0) s(u)
```

相比当前三次smoothstep `3u²-2u³`，这条五次轨迹的起点和终点加速度也为0，
更适合从hold接入新chunk。

两者的直观差别是：

```text
cubic:   s(u)=3u²-2u³
         起止速度为0，但端点加速度不为0

quintic: s(u)=10u³-15u⁴+6u⁵
         起止速度和加速度都为0
```

所以quintic不一定显著降低“最大位置步进”，但理论上能降低接入瞬间的加速度折角
和jerk。研究时不能同时改变融合时长、内部weight或调度模式，否则无法判断改善来自
曲线还是来自机器人整体变慢。

第一轮严格单变量A/B固定75K、Split、Sync、120ms、双臂内部weight 10、相同初始
姿态和物体位置；A只使用cubic，B只替换为quintic。运行时切换命令为：

```bash
./scripts/05_powered_sync.sh --continuous \
  --boundary-blend-profile quintic_smootherstep
```

不传`--boundary-blend-profile`时仍使用冻结的cubic基线，因此可立即回退。telemetry的
`runtime_start.boundary_blend_profile`必须与本轮选择一致，避免混淆A/B日志。
再各做至少3轮短时powered。主要比较双臂边界窗内实际最大步进、速度、加速度、
jerk、发送覆盖率，以及抓取/放置是否变钝。只有边界动力学下降且任务行为不退化，
才进入T1/T2自适应时长实验。

对这个标准minimum-jerk轨迹，峰值大致按以下规律变化：

```text
max velocity     ≈ 1.875 |q1-q0| / T
max acceleration ≈ 5.774 |q1-q0| / T²
endpoint jerk    ≈ 60    |q1-q0| / T³
```

因此融合时间不能与跳变大小脱离。对相同跳变，把60ms延长到120ms会使这个
估算jerk降低约8倍。

当新chunk终点不是静止目标时，完整方案不应只用上述简单式，而应用广义五次
Hermite连接：

```text
起点：当前已下发的 p0, v0, a0
终点：新chunk在T时刻的 p1, v1, a1
```

Sync基线中旧chunk结束后已经hold约0.5秒，所以起点可以先按`v0=0,a0=0`处理。
真正的旧轨迹速度匹配更适合未来Async/重叠chunk调度，不是当前Sync的第一步。

## 4. Chunk阈值和拒绝策略

### 4.1 不用一个阈值管所有问题

需要分开以下门禁：

| 门禁 | 解决什么 | 建议行为 |
|---|---|---|
| 合同门 | shape不是`50×34`、NaN/Inf | 硬拒绝 |
| 物理限位门 | 绝对位置超关节限位 | 小幅clip并记录；大幅硬拒绝 |
| 起点跳变门 | measured/current target到新chunk起点过大 | 分级处理 |
| 动力学门 | 速度、加速度、jerk过大 | 尝试可行桥接；不可行则拒绝 |
| Servo tick门 | 最终100Hz相邻命令过大 | rate limit或硬故障，不与chunk门混用 |
| 手部5Hz门 | 相邻`move_ee_pos`变化过大 | 只对边界做有界渐进 |

手部和双臂必须使用不同的阈值。最新日志中双臂chunk内步进P95约0.017～0.019rad，
而双手5Hz步进P95约0.24～0.37rad；用同一个0.05rad阈值会把正常闭手也拒绝。

### 4.2 建议的三级处理

不建议“小于阈值执行，大于阈值全部拒绝”。建议使用：

```text
小跳变区：正常接入或使用最短融合时间
可融合区：根据速度/加速度/jerk上限计算minimum-jerk所需时间
硬拒绝区：所需融合时间过长、超物理限位，或模型输出明显异常
```

对每个双臂关节，可以从以下三个约束估算桥接时间：

```text
T_velocity >= 1.875 * delta / velocity_limit
T_accel    >= sqrt(5.774 * delta / acceleration_limit)
T_jerk     >= cbrt(60 * delta / jerk_limit)

T_required = max(T_min, T_velocity, T_accel, T_jerk)
```

所有双臂关节取最大`T_required`作为同步桥接时间。如果该时间小于已验证的
`T_max`，则进行minimum-jerk桥接；否则拒绝该chunk。

第一轮不立即上自适应时长，以免同时改变多个因素。建议先比较：

1. 60ms cubic smoothstep当前基线；
2. 120ms cubic smoothstep；
3. 120ms quintic minimum-jerk；
4. 前三者定出稳定方向后，再引入基于`T_required`的自适应时长。

### 4.3 拒绝chunk后怎么做

“拒绝”和“操作员暂停”不是一回事。
还要区分“门禁已计算”和“门禁正在强制拒绝”：当前正式
`05_powered_sync.sh`使用Split control profile，首跳、裁剪幅度和动力学超限
目前是warning-only，不因这三类告警拒绝chunk。Shape、finite、HTTP/GDK失败等
硬错误仍会阻止执行。以下是强制安全门开启时的拒绝状态机。

当前Powered-sync的实际逻辑是：

```text
拒绝chunk
  → 取消当前playback
  → hold最后一个已验证安全目标
  → 下一轮重新采集图像和state
  → 重新HTTP推理
```

如果还没有任何已接受目标，例如第一个chunk就被拒绝，Servo保持零硬件发送。
它不会继续外推旧chunk，也不应重放旧chunk。

当前代码可以一直重试，直到新chunk通过、达到`max_requests`或操作员停止。
平滑阶段建议将这个策略收紧为：

```text
第1～2次连续拒绝：hold + 重新观测 + 重新推理
第3次同类原因连续拒绝：保持safe hold，不再自动请求，需操作员确认后重新观测
```

原因是连续大跳变可能表示模型与当前姿态、场景或输入合同存在系统性不一致。
无限高频重试只会浪费推理，也会让现场人员不清楚机器人是在hold还是即将突然恢复。

连续拒绝次数、是否必须人工resume仍是待讨论参数，本文建议值为3次。

## 5. 方案优先级与解决范围

| 优先级 | 方案 | 主要解决 | 不解决 | 主要风险 |
|---|---|---|---|---|
| P0 | 实际下发telemetry | 定位真实抖动、调参和归因 | 本身不会平滑 | 日志量过大，应每chunk汇总 |
| 已验证基线 | 双臂120ms cubic边界融合 | 新chunk接入时的边界跳变 | chunk内尖峰、网络停顿 | 继续加长会使响应变钝 |
| P1 | 双臂chunk内部离线平滑选型 | waypoint内部速度折点和jerk尖峰 | 网络停顿 | 过强会改变策略语义 |
| P2 | 双臂chunk边界quintic minimum-jerk | 边界加速度连续性 | chunk内尖峰、网络停顿 | 当前边界已非主要峰值来源 |
| P1 | 启动双臂ease-in | 第一个chunk从静止猛冲 | 后续chunk边界 | 启动变慢，需和首跳门联动 |
| P1 | 首条O10命令安全门 | 不可信全零反馈被当作hold/ease起点 | 正常手部边界 | 不应用measured zero对手部缓入 |
| P2 | 双手边界有界渐进 | 5Hz O10跨chunk大跳 | 双臂抖动、网络停顿 | 过慢会错过抓取时机 |
| P2 | 双臂100Hz rate limiter | 最终Servo tick过大 | 模型语义不连续 | 连续限幅会产生跟踪滞后 |
| P1候选 | chunk内zero-phase轻量平滑 | 单chunk内高频反向小抖动 | 边界跳变、网络停顿 | 可改变接触时序，必须固定端点 |
| P4 | 局部EMA | 持续小幅在线噪声 | 网络停顿、大跳变 | 相位滞后和抓取不到位 |
| P4 | 迟滞deadband | 量化附近的微小来回波动 | 明确开合手动作 | 普通死区会粘滞后突跳 |
| P4 | Async/时间对齐重叠chunk | Sync的HTTP hold停顿 | 本身不保证边界平滑 | 观测陈旧，当前实测边界更差 |

## 6. 各阶段的具体方案

### 6.1 启动阶段

双臂：

- 第一个合法chunk到达前保持零硬件发送；
- 合法chunk到达后重新读取live arm state；
- 用minimum-jerk从live arm state接入新chunk；
- 融合前仍要过绝对限位和动力学门。

双手：

- 不使用重启后的20D measured zero作ease-in起点；
- 第一条命令只允许来自已验证模型目标，或未来正式批准的safe hand command；
- 第一条O10命令必须完整记录，不能只记录原始chunk。

### 6.2 Chunk边界

当前Sync是：

```text
旧chunk结束 → hold → HTTP推理 → 新chunk
```

因此第一阶段桥接是“hold target→新chunk”，而不是“旧chunk未来轨迹→新chunk”。
只有将来重新启用Async或提前请求时，才能做真正的新旧轨迹时间对齐和速度匹配。

双臂边界先做120ms分级实验；双手保持5Hz硬件通道，另外做边界专用ramp。
不把34D重新合并成统一Servo请求。

### 6.3 Chunk内部

当前30→100Hz已经是按连续时间的线性插值，不是重复waypoint。模型的“50”是
chunk中有50个waypoint，不是50Hz。

Chunk内平滑只在实际下发telemetry确认存在高频反向抖动后再开启，并且：

- 第一轮只处理双臂前14D；
- 固定或重新约束首尾位置；
- 平滑后重新计算位置、速度、加速度和jerk门；
- 不默认平滑O10，避免改变闭手时机。

2026-08-04已用三轮powered telemetry做第一轮离线回放，共71个实际下发chunk。
工具入口为：

```bash
./scripts/analyze_chunk_smoothing.sh \
  logs/telemetry/powered/g2_powered_split_sync_40s_20260804_160127.jsonl \
  logs/telemetry/powered/g2_powered_split_sync_40s_20260804_160332.jsonl \
  logs/telemetry/powered/g2_powered_split_sync_40s_20260804_161825.jsonl
```

工具只读取JSONL，不导入robot adapter，不连接GDK。它复用正式运行的30→100Hz
时间语义，排除每个chunk开头已记录的60ms/120ms边界窗，只处理双臂前14D，并固定
模型轨迹首尾点。

三轮合并的首轮结果：

| 候选 | chunk最大步进P95 | jerk P95 | 轨迹偏差P95/最大值 |
|---|---:|---:|---:|
| 原始线性插值 | 0.01670rad | 5454rad/s³ | 0 / 0rad |
| FIR5零相位 | 0.01555rad | 2308rad/s³ | 0.00167 / 0.00844rad |
| jerk正则，权重10 | 0.01534rad | 1803rad/s³ | 0.00199 / 0.01156rad |
| jerk正则，权重100 | 0.01450rad | 1726rad/s³ | 0.00224 / 0.01350rad |
| jerk正则，权重1000 | 0.01399rad | 1305rad/s³ | 0.00283 / 0.02793rad |
| jerk正则，权重10000 | 0.01185rad | 933rad/s³ | 0.00451 / 0.05852rad |

最新120ms单轮中，FIR5把jerk P95从5210降到2048rad/s³，约下降61%；但chunk
最大步进P95只从0.01708降到0.01563rad，约下降8.5%。权重100的jerk正则可降到
0.01480rad，但最大轨迹偏差达到0.01122rad。

这说明轻量平滑对jerk很有效，但仅靠温和滤波还达不到“最大步进下降约30%”的原始
目标。权重10000能使chunk最大步进P95下降约29%，但最大轨迹偏差达到0.05852rad
（约3.35°），可能改变接触和抓取语义，排除作为首个真机候选。当前离线折中候选为
权重10的固定端点jerk正则。

权重10已接入正式模块化客户端并完成两轮powered验证：

- 参数为`--arm-internal-jerk-weight`，允许范围0～100；低层CLI默认0；
- 只修改前14D双臂，后20D双手逐元素保持不变；
- 50点chunk的第0和第49个双臂waypoint严格固定；
- 在原始关节限位裁剪后平滑，平滑后再次经过关节限位裁剪；
- 首跳检查、速度/加速度/jerk检查使用平滑后的实际候选轨迹；
- `action_chunk`额外记录权重、平滑偏差P95、最大偏差及对应关节；
- 离线评估和真机运行复用同一个`trajectory_smoothing.py`实现，避免算法漂移。

两轮合并共47个实际chunk的同轨迹反事实中，chunk最大步进P95从0.01485降到
0.01314rad，约下降11.5%；内部jerk P95从4948降到1491rad/s³，约下降70%；最大
轨迹偏差0.00836rad，且无Servo故障、safe hold、裁剪或动力学告警。因此正式Sync
Shell入口冻结注入120ms和权重10；低层CLI和Async保持0关闭，仍可显式做回退A/B。

### 6.4 灵巧手5Hz平滑离线第一轮

双臂参数冻结后，手部作为独立阶段处理。旧日志只有每chunk手部汇总，没有逐条20D
命令，因此第一轮对两次powered、共47个chunk按80ms首采样和标称5Hz做策略回放。
入口为：

```bash
./scripts/analyze_hand_smoothing.sh LOG1.jsonl LOG2.jsonl
```

主要结果：

| 候选 | chunk最大步进P95 | 全局最大步进 | 跟踪误差P95/最大值 | chunk末误差P95 |
|---|---:|---:|---:|---:|
| 原始标称5Hz | 0.4527rad | 0.7284rad | 0 / 0rad | 0rad |
| 手部jerk权重10 | 0.4267rad | 0.7328rad | 0.0114 / 0.0462rad | 0.0089rad |
| 因果cap 0.30 | 0.3000rad | 0.3000rad | 0.0629 / 0.4284rad | 0.0671rad |
| 因果cap 0.35 | 0.3500rad | 0.3500rad | 0 / 0.3784rad | 0.0175rad |

相同weight 10对手部chunk最大步进P95只改善约5.7%，全局最大值反而略升，证明不能
直接复用双臂参数。0.30及以下硬限幅会造成明显跟踪滞后；0.35～0.40可能只处理少数
尖峰，但旧日志的标称回放全局最大值0.7284rad明显高于实际汇总约0.44～0.47rad，
说明5Hz相位和真实成功命令不可忽略，目前不据此选择上线参数。

Telemetry现已在每个`dispatch_summary`增加`hand_commands_rad`、

GDK命令，每chunk约8条、结束时一次性写盘，不改变手部控制。下一轮保持手部原逻辑
采集后，再用真实序列选择手部独立jerk或因果bounded ramp。

#### 6.4.1 cap40的结论

`cap40`表示每个5Hz tick、每个手指关节最多变化0.40rad。它不是主平滑算法，当前也
没有接入真机发送链路，只是离线反事实候选。最新两轮5-step推理日志的47个真实chunk
中，单独使用cap40得到：

| 指标 | 实际成功命令 | 仅cap40 |
|---|---:|---:|
| 全部步进P95 | 0.3120rad | 0.3084rad |
| 边界步进P95 | 0.4617rad | 0.3841rad |
| 全局最大步进 | 0.6466rad | 0.4000rad |
| 最大瞬时跟踪误差 | 0rad | 0.2466rad |

因此cap40对普通步进P95只改善约1.2%，不能解释为“手已经平滑”；它的价值只是拦住
少数极端跳变。被截断的残差还可能在后续tick追赶，所以cap40只保留为最终安全兜底，
不能单独上线。

#### 6.4.2 离线第二轮：V1因果手部跟踪器

第一版先由离线评估器验证；2026-08-05已将同一状态跟踪器接入Split的5Hz发送前路径，
但尚未完成首次powered验证。数据流为：

```text
真实记录的5Hz原始20D目标
  → 从上一条成功命令开始的400ms cubic边界guide
  → 持续速度/加速度跟踪器
  → 大幅方向反转保护
  → 0.40rad最终单步安全cap
```

设计约束：

- 边界锚点使用上一条已经被`move_ee_pos`确认成功的20D命令；不使用重启后可能全零的
  measured hand state；
- 400ms对应约两个5Hz控制周期。guide结束后不能直接切回raw target，状态跟踪器必须
  继续运行到误差自然追上，避免把边界跳变搬到chunk内部；
- 每个Sync chunk之前存在hold，因此chunk接入时速度状态重置为0，但位置状态继承上一条
  模拟成功命令；拼接多个日志时如果真实锚点不连续则自动重新锚定，不能跨运行串状态；
- V1统一参数暂取最大速度2.0rad/s、最大加速度10.0rad/s²、方向反转误差门0.15rad，
  仅用于筛选算法结构，尚不是O10分关节物理上限；
- 时间戳只在0.5～1.5个标称5Hz周期内参与积分，防止线程延迟反而授权更大位置跳变；
- 方向反转保护只处理误差大于0.15rad的反向变化。首个原型对所有反向变化强制停一拍，
  曾造成4个关键半程事件错过和0.143rad chunk末P95误差，已明确排除。

同一V1在真实成功命令上的首轮结果：

| 数据 | 候选 | 边界P95/最大 | 全局最大 | 内部P95 | 跟踪P95 | chunk末P95 | 时序P95/错过事件 |
|---|---|---:|---:|---:|---:|---:|---:|
| 10-step，67 chunks | 实际 | 0.2905/0.5365 | 0.7292 | 0.3153 | 0 | 0 | 0/0 |
| 10-step，67 chunks | V1 | 0.0553/0.1730 | 0.4000 | 0.3285 | 0.0589 | 0 | 0.20s/0 |
| 5-step，47 chunks | 实际 | 0.4617/0.6466 | 0.6466 | 0.3061 | 0 | 0 | 0/0 |
| 5-step，47 chunks | V1 | 0.1186/0.1907 | 0.4000 | 0.3133 | 0.0392 | 0 | 0.20s/0 |

V1已经把两个数据集的边界最大值压到0.20rad以内，未错过半程事件，且chunk末P95
误差为0，说明固定时窗结束后的残差没有普遍积累。但它仍有三个不能直接上机的问题：

1. 内部步进P95在两组数据上分别增加约4.2%和2.4%，说明追赶过程仍会把一部分运动
   转移到内部；
2. 5-step数据的最大瞬时跟踪误差仍为0.5266rad，P95时序偏移为一个5Hz周期；
3. 统一20D速度/加速度参数没有区分拇指旋转、MCP、PIP和指间开合关节，不能当作
   已验证物理限制。

离线阶段结束时，V1作为可回退的首个powered候选接入；后续首次真机结果见6.4.3。
正式Sync脚本显式使用`--hand-smoothing-profile v1`；Async和低层CLI默认
`off`，可立即回退。运行时与离线评估复用`CausalHandCommandTracker`，避免两套算法
漂移。第一条手部命令没有本进程内可信成功锚点时保持原启动行为，不使用重启后可能
全零的反馈；从后续chunk开始用本进程上一条成功命令锚定。

安全实验原则仍是先运行10秒空场景，并检查新增telemetry：raw/filtered 20D、tracking error、
边界激活次数、速度/加速度限制、方向反转和cap命中。若出现回退、闪现、内部追赶或
抓取时序明显延迟，立即回退`--hand-smoothing-profile off`，不继续完整任务。

#### 6.4.3 V1首次powered结果与阶段结论

2026-08-05完成一轮约170秒、71个完整chunk的V1 powered Sync运行，日志为
`g2_powered_split_sync_170s_20260805_160434.jsonl`。运行明确记录
`hand_smoothing_profile=v1`，手部有效发送约4.90Hz，每chunk 8～9条成功命令；全程
没有Servo failure、safe hold、HTTP失败或GDK错误。

优先使用同一轮raw target与filtered command的成对反事实，避免把不同场景和策略输出
差异误认为算法收益：

| 指标 | Raw目标 | V1实际命令 | 变化 |
|---|---:|---:|---:|
| 边界步进P95 | 0.1534rad | 0.0357rad | 降低76.7% |
| 边界最大步进 | 0.4262rad | 0.2121rad | 降低50.2% |
| 全部步进P95 | 0.2705rad | 0.2628rad | 降低2.8% |
| 内部步进P95 | 0.2793rad | 0.2851rad | 增加2.1% |
| 全局最大步进 | 0.4408rad | 0.4000rad | cap40生效 |
| tracking error P95 | 0 | 0.0194rad | 引入小幅跟踪差 |

结论是400ms cubic边界guide已经真实有效，但V1还不能冻结为最终手部配置：

- 71个chunk中7个触发cap40，共35个关节tick；部分raw单步只有约0.287rad，残差追赶
  却形成0.40rad实际步进，说明边界冲击有少量被转移到chunk内部；
- 方向反转保护在6个chunk、25个关节tick命中。request 64最后一拍正常张手被延迟，
  三个半程事件未在chunk内完成，chunk末最大误差0.196rad；
- 最大瞬时tracking error为0.373rad；大多数命令误差很小，但尾部少数事件仍可能影响
  精密交接时序；
- 当前10rad/s²加速度限制命中0次，尚未形成实际约束，不能把存在参数等同于已生效。

阶段冻结决定：保留V1代码和可回退开关，暂停继续真机调参。恢复工作后的两个优先修改
是：方向反转保护只作用于400ms边界阶段；追赶残差使用小于cap40的独立catch-up预算，
禁止raw约0.28rad时filtered追赶到0.40rad。修改后继续用同一raw/filtered telemetry
验收，不能只比较跨轮日志。

#### 6.4.4 2026-08-26 10Hz复核：内部追赶仍未消失

新网络下两轮10Hz Sync共56个chunk，runtime明确记录V1、400ms guide、2rad/s速度上限和
10rad/s²加速度上限均启用。两轮双手实际最大jerk的chunk分布分别为
P50/P95/max 24.5/156.9/171.3与14.4/131.6/249.6rad/s³；最大单步两轮P95均约
0.20rad。最坏chunk的raw 20D jerk为5720.5rad/s³，而V1实际命令最坏jerk为
249.6rad/s³，说明平滑显著削弱了原始目标尖峰，但没有消除chunk内部追赶。

两轮速度/加速度限制分别命中8/9与36/46个joint tick，方向反转保护和0.40rad最终cap
均未命中。结合6.4.3的同轮raw/filtered配对结果，操作者观察到的内部抖动与已知机制一致：
问题不是V1未生效，而是边界残差仍可能在后续命令中较快释放。下一步保持10Hz、网络、模型
和任务不变，先离线验证“边界期反转保护 + 独立catch-up预算”的V1.1；不能通过继续降频或
把双臂weight10直接套到手部来掩盖问题。

随后两轮复测`174634`与`174804`分别得到18和12个chunk，操作者明确报告“很抖”。与
此前56个chunk合并基线按同口径比较：手部实际最大jerk P95从137.9升至157.0rad/s³，
`jerk>100rad/s³`占比从12/56（21.4%）升至8/30（26.7%）；手部最大单步P95仍约
0.20rad。与此同时最新两轮边界首步P95只有约0.002--0.003rad，最坏内部jerk仍集中在
左右index/middle/ring/pinky PIP关节。该证据排除“边界guide未启用”，并再次指向guide
之后的内部追赶释放。

最新raw模型chunk jerk P95为1803rad/s³，低于此前2623rad/s³；因此不能把更明显的主观
抖动解释成这次模型原始轨迹整体更坏。第一轮request 16/17的手部起点跳变为0.502/0.370rad，
随后出现一次O10 `move_ee_pos failed`；第二轮request 5起点跳变0.580rad，同时发生独立的
1.420s模型/CUDA长尾。决定升级为：当前V1暂停继续Powered，先完成V1.1离线反事实和
单变量短门禁。

### 6.5 EMA和deadband

不启用全局34D EMA。EMA会对所有轨迹引入相位滞后，可能加重抓取不到位和放置偏移。

如果将来确认某些关节只有微小量化波动，deadband必须是带迟滞和累积误差的版本：

```text
小变化累积但暂不发送
累积量未超阈值：保持上一命令
累积量超阈值：发送累积后目标并清空误差
```

普通“小于阈值就丢掉”的死区会在长时间积累后突然大跳，不作为候选。

### 6.6 归一化

DM0.5服务器负责根据训练`norm_stats`对模型输入/输出做合同一致的归一化和
反归一化。G2客户端接收的应当已经是单位为rad的绝对关节位置。

不在客户端重新对动作做一次归一化，也不在归一化空间直接使用统一的平滑阈值。
不同关节可以使用历史数据分位数或物理限制生成“归一化异常分数”用于检测，
但最终轨迹、速度、加速度、jerk和安全门仍在rad单位下计算。

## 7. 网络延迟与轨迹平滑的边界

当前Sync周期是：

```text
播放49个30Hz区间，约1.633秒
  → hold
  → 采集新观测
  → HTTP等待约0.47～0.52秒
  → 接入新chunk
```

Minimum-jerk可以让“hold后重新接入”不猛冲，但不能删除hold时间。
真正去停顿需要提前观测/推理、更低推理延迟或新旧chunk的时间对齐重叠。

现有Async已经能隐藏大部分HTTP等待，但最新实测双臂跨chunk和双手跨chunk跳变更大，
并且存在陈旧前缀。因此网络/调度优化是P4独立实验，不与第一轮minimum-jerk同时开启。

## 8. 实验顺序与验收

全部实验保持75K、Split和Sync不变，每轮只改一个因素：

1. 实际下发telemetry和首条O10命令记录已实现，纯逻辑测试已通过；
2. 两轮60ms和一轮120ms cubic真机对比已完成，120ms边界改善已确认；
3. 三轮、71个实际下发chunk的内部平滑离线回放已完成第一轮；
4. 高权重扫描已完成并排除权重10000；双臂权重10已完成powered验证并冻结到正式
   Sync入口；
5. 10-step 67个和5-step 47个chunk的真实手部5Hz序列已完成离线回放；仅cap40被排除
   为主平滑算法；
6. 手部V1已完成71个chunk的首次powered验证：边界改善成立，但内部P95增加2.1%，
   暂不冻结为最终配置；
7. 下次从“边界期反转保护+独立catch-up预算”继续，再做固定物体A/B和分关节统计；
   边界quintic、
   EMA、deadband和Async不与手部实验同时改动。

每个候选在固定雪碧/橙汁场景至少重复3次，记录：

- 双臂边界100Hz步进的P95和最大值；
- 双臂最大速度、加速度和jerk；
- 双手5Hz实际命令的P95和最大值；
- 平滑后目标跟踪误差和连续限幅次数；
- 抓取成功、碰瓶、抓紧不放和放置偏移；
- 可见停顿和首次启动冲击。

候选方案不仅要“肉眼更顺”，还应至少满足：

- 目标边界指标相对基线降低约30%；
- 不增加GDK错误、watchdog或安全门拒绝；
- 抓取成功率不明显退化；
- 放置偏移和闭手延迟不明显增大。
