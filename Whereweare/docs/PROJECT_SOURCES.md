所有注册表路径相对于工作区 `Projects/`，不是相对于 `Whereweare/`。`source_paths` 指向用于项目摘要的权威入口，`watch_paths` 指向允许发现变更的 Markdown 文件或目录。加入观察范围不代表其中全部历史内容都是当前任务。

注册表中的 `status` 和 `stage` 表示来源接入范围与核验边界，不是机器人或训练服务的实时状态。动态内容应从声明的来源读取，事实必须能回到原文。

`priority` 仅保留兼容字段，统一 P2，不作为用户主次依据。主线／支线／共享工具由网页人工设置，独立持久保存；没有用户确认前不按文件活跃度推断优先级。

`evidence_date` 只填写源文档明确给出的证据日期，未知使用 `null`；不使用文件修改时间。它是初始关联时的证据锚点，不应覆盖后续文档中的日期，也不等同于最后同步时间。服务是否存活、设备是否恢复和新实验是否完成，都需要各自的新记录。

里程碑只登记来源明确给出的交付目标或下一步。初始 `planned` 表示来源列出了计划而没有完成确认；它不代表已排入今天。没有可靠专项路线图时保留空列表，不由通用研发模板生成假进度。里程碑的完成更新应附新的原始依据；不根据提交数量、文档长度或历史检查框计算完成率。

## 新增或补齐项目

1. 在所属项目内选定已有的唯一状态入口与任务大纲；没有时先在所属项目建立，再关联到中台。
2. 在注册表增加稳定的 `id`、中文名称、交付/工具类型和简短职责。积木项目已有 `block-sort`，补齐时保留该 ID。
3. 在 `source_paths` 指定少量权威 Markdown 入口，在 `watch_paths` 指定相关文档目录。不要加入整个 Projects、模型权重、数据集、运行产物或上游源码树。
4. 仅录入能从来源解释的日期与里程碑；未知保持 `null`、空列表或 `unknown`，在 `warnings` 写清证据缺口。
5. 触发中台同步，核对项目摘要、来源链接和新变更是否归属正确；新增来源需要先遵循其父目录的协作约定。

归档、历史、`frozen`、`superseded`、`archived` 文档用于追溯，不自动导入当前待办。同一份活跃状态文档里的历史段落也需要保留时点语义。文档变更检测和规则提取无法自行完成所有语义核对；出现新旧冲突时应显示来源与警示，再读相关段落。

本次关联只读取任务说明、文档索引和状态入口，没有遍历项目代码，也没有修改上游文档。后续协作应先读取中台 briefing，再按变化范围读取必要来源。

平台使用 platform（F1/G2/shared）；工具用 supports 关联任务。activity_paths 仅供显式审阅时读取 Git 元数据，不扩大文档扫描范围。手机装盒、Book 按用户确认是早期构想；目录覆盖不等于首页展示。
