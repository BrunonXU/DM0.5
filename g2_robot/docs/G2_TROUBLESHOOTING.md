# G2 × DM0.5 踩坑与故障经验

本页记录已经定位的问题。上机固定流程见`00_G2_OPERATOR_GUIDE.md`。

## 头部相机持续`Frame is null`

- 现象：关节DDS、`mode=5`和左右腕相机正常，但
  `/camera/head_color`连续返回空帧。
- 已排除：不是DM0.5网络问题，也没有其他Python G2/Camera进程占用。
- 本次根因：G2上半身重启前，头部相机发布链路未正常工作。
- 本次处理：按机器人正常流程重启上半身后，头部、左腕、右腕三路相机全部恢复，
  预检通过。
- 约束：相机恢复前不得用黑图替代，也不得进入Shadow或powered。
- 注意：上半身重启后若日志目录出现`19700101`，先检查系统时间是否重新同步。

## GET返回405

- 现象：curl返回405。
- 原因：`/process_frame`只接受multipart POST。
- 处理：将405视为端口可达；000、timeout、refused才是网络失败。
- 验证：Shadow成功返回`50×34`。

## GDK环境导致curl符号错误

- 现象：`curl_global_trace`或`CURL_OPENSSL_4`错误。
- 原因：`env.sh`后的`LD_LIBRARY_PATH`让系统curl加载了GDK附带的libcurl。
- 处理：`env -u LD_LIBRARY_PATH /usr/bin/curl ...`。
- 验证：返回405。

## G2能连笔记本但不能直连6000D

- 历史原因：Windows VPN/公司WLAN路由不会自动共享给G2，曾临时把服务器端口转发
  到笔记本`10.42.1.10:17891`。
- 当前链路：G2通过公司内网直连6000D `10.130.153.114:7892`，不再经过Windows。
- Docker坑：bridge容器的回复曾被6000D策略路由送入Meta虚拟接口，形成非对称路由；
  主机本地curl正常，但G2请求超时。
- 当前处理：75K容器使用host network监听7892；G2 GET返回405且Shadow POST成功。

## Config request timeout

- 现象：`Failed to get config parser`、`JointServoControl failed`。
- 原因：独立恢复程序创建了`Robot()`，但没有调用`gdk_init()`。
- 处理：每个进程完整执行`gdk_init → Robot/Camera → gdk_release`。
- 验证：同一进程内exact-current hold通过。

## MotionControlStatus为空

- 原因：DDS刚启动，立刻读取状态。
- 处理：初始化后等待，preflight默认等待10秒。
- 验证：连续读取`mode=5,error_code=0`。

## PTP设备警告

- 现象：`No valid PTP device found`。
- 结论：当前客户端使用本机monotonic时钟，它不是Config Manager失败的直接原因；
  跨设备精确同步前仍需修复PTP。

## 单独发送一个手指关节无效

- 现象：Python调用可能返回，但GDK日志出现`Param ... not found`，实机不动。
- 原因：o10_t2不能按该方式单关节独立发送。
- 结论：17D×2和单手独立实验已撤销；正式路径使用Split：双臂14D Servo与双手
  20D `dual_tool move_ee_pos`。不要恢复旧`test.py`或单关节发送路径。

## 重启后O10全0反馈原样回发导致拇指顶相机

- 现象：上半身重启后，左右O10的20个position连续读取均为0，健康字段看起来正常；
  但17D×2、单手`move_ee_pos`和统一34D三种首次控制实验都曾使双拇指明显上翘。
- 最新证据：统一34D powered启动时，模型动作尚未执行，后台current-hold已经使
  拇指接触相机；随后模型chunk因`0.2504rad > 0.20rad`被拒绝。
- 官方语义：GDK 2.6.3把左右O10的10个全零命令都定义为“开手”。
- 直接原因：旧powered在模型动作到达前，把重启后的20D零反馈当作current-hold
  命令发出；机器人因此执行开手，拇指沿开手轨迹向上接触相机。这不是模型先输出
  了全零动作。
- 边界：仍不能仅据此判定零反馈本身是硬件传感器故障；已确定的是“零反馈可以读取，
  但在命令语义中不是安全保持姿态”。
- 当前修复：首个模型目标接受前零硬件发送；正式路径改为Split；Servo hold、复位和
  拇指微动execute均软件锁定。Powered Split已完成真实抓取测试。

### 与最初原始客户端的历史对照

- 成功版默认发送路径：`left_arm 7 + right_arm 7 + left_hand 10 + right_hand 10`
  合并为一次统一34D `joint_servo_control`。
- 成功版默认通道：`enable_low_latency=True`、100Hz；没有碰撞保护。
- `move_ee_pos`在成功版中只是可选双手后端，配置后独立以5Hz发送；默认未启用。
- 成功版的Servo worker启动后先等待`_has_target_event`；首个真实策略目标到达之前
  不调用任何运动API。首次目标到达后，以live state为锚在约60ms内smoothstep接入。
- 当时新版的回归：powered创建ServoStreamer时直接把初始state设成hold目标，并在
  推理前启动线程；当O10初始state为不可信全0时，模型动作尚未返回，双手已经收到
  全0绝对位置命令。
- 成功版对O10没有固定offset或零点变换，只有官方限位裁剪。当前优先修复启动发送
  时序，而不是猜测并添加offset。
- 2026-07-31已完成并真机验证最小修复：Powered首个接受chunk前Servo零发送；
  0.9rad首跳被拒绝时发送次数为0且手指不动。

## 100Hz插值与Servo tick lateness

- 30→100Hz线性插值只负责每10ms计算目标，不会让GDK/DDS调用自动变快。
- `tick lateness=0.044158s`表示首周期错过100Hz截止时间44ms，不等价于已经证明
  normal通道稳态只能约23Hz。
- 首周期还包含首次baseline状态读取、GDK/DDS冷启动和可能的O10激活；当前watchdog
  在第一轮停止，尚无稳态样本。
- 后续必须分别记录状态读取、单次发送、首次tick和稳态tick的P50/P95/P99；在手部
  首次控制问题解决前，不通过放宽watchdog继续真机发送。

### 2026-07-31巨抖与2.53秒Servo阻塞的新证据

- powered日志显示HTTP推理稳定约0.46～0.58秒，故网络不是100Hz周期内的直接阻塞。
- 同一轮GDK原生日志中，统一34D的每次请求都能验证14个双臂参数，但20个O10参数
  几乎逐次全部出现`Param ... not found`；1104次发送对应约22080次错误查找。
- 故障前一次请求在验证第一个左拇指参数后，配置解析内部停顿约2.530秒，再继续
  验证第二个参数；它与Python watchdog记录的2.531735秒严格对齐。
- 结论：30→100Hz线性插值仍按时生成目标，但统一34D GDK请求里的O10参数解析路径
  已被证明异常。隐藏日志不能修复该阻塞。
- 处理结果：`arms-only`完成隔离；`split`使用双臂100Hz Servo和O10双手5Hz
  `move_ee_pos`并通过真机验证。Split现为正式默认，统一34D只保留历史诊断。

### 旧客户端为何可能更平稳

- 普通默认配置还启用了关节EMA，`alpha=0.35`。
- 每次新目标会从当前通道目标经过约60ms smoothstep，而不是瞬时替换。
- 双臂另有每个Servo tick约`0.006rad`的最大步长限制。
- O10若选`move_ee_pos`后端，则只以5Hz发送最新手部目标，且与双臂线程独立。
- 但旧代码也存在显式profile会关闭EMA/步长限制；目前没有旧运行命令足以证明现场
  当时具体用了哪组开关。因此先隔离接口和频率，再决定是否逐项恢复平滑，避免把
  根因和表面抑制混为一谈。

### split真机30秒验收结果

- 18/18个chunk成功，HTTP P50约0.478秒、P95约0.520秒。
- 双臂3804次发送，按整段运行时间约98.5Hz；双手190次发送，约4.9Hz。
- `move_ee_pos`末次耗时0.000283秒；三段GDK原生日志中没有O10
  `Param ... not found`、Config timeout或Servo watchdog。
- 机器人从巨量抖动改善为轻微抖动，并完成雪碧抓取；证明统一34D内的O10解析
  路径是此前主要故障源，拆分接口有效。
- powered-sync仍然在每个1.633秒动作段后等待约0.48～0.52秒推理。日志中相邻
  chunk到达间隔中位数约2.134秒，因此肉眼可见的周期性停顿不能靠30→100Hz插值
  消除。
- 双臂模型轨迹本身较平滑：chunk内30Hz步进P95约0.0095rad，跨chunk最大约
  0.0418rad。手部跨chunk最大约0.2734rad且以5Hz更新，更可能出现局部手指小跳。
- 当前不建议直接给全部34D加入EMA：它会引入相位滞后，可能让已经出现的放置偏差
  更严重。若后续确认仅手部抖，应只对O10通道做有界平滑。

## low-latency不报碰撞

- 原因：官方2.6.3明确说明该通道没有碰撞保护，不是碰撞被解决。
- 处理：不得在normal失败后自动回退。当前正式Split配置明确使用low-latency双臂，
  每次都要求`ok`、5秒倒计时和专人握住物理急停；O10双手走独立`move_ee_pos`。

## Powered运行约6.53秒后停止

- 现象：4个完整chunk后不再动，重启仍不动。
- 原因：后续chunk首动作相对当前state跳变约0.18～0.21rad，超过0.05rad安全门。
- 结论：模型服务器仍在返回；安全门正常阻止了不连续动作。
- 处理：不要提高阈值，改用短前缀和跨chunk连续调度。

## 手抓紧瓶子

- 原因：模型后续动作明确闭合左手，不是单纯Servo抖动。
- 处理：托住物体并按`q`干净退出VLA；若未重启、未人工掰动、未使用物理急停且
  最后成功命令在30分钟内，可执行批准的Split Home。否则走人工恢复。

## 灵巧手Home如何确定

- 官方可用接口是`move_ee_pos(group=dual_tool,target_type=o10_t2)`，输入左右各10个
  关节角；官方没有提供独立于具体机器人净空的“一键安全复位”姿态。
- 第1条成功命令最大仅0.001925rad，实际是60ms smoothstep刚开始的近零采样，造成
  手指短暂晃动；它不是原始姿态，不能作为Home。
- 第9条成功命令与H5首帧最大只差0.007194rad，操作者肉眼确认手指已回到初始位置，
  因此固化为批准Home。
- 独立新GDK会话直接调用`dual_tool move_ee_pos`连续拒绝了原样重发的成功锚点，
  因此复位复用已验证Split控制上下文。2026-08-04真机确认锚点和一步Home均成功。
- 当前完整复位先让双手从30分钟内最后命令以5Hz最多8步回Home，再让双臂以100Hz、
  默认5秒回到800条H5第0帧14D中位数；双臂部分仍待首次真机验收。不能使用重启零反馈。

## clip次数很大

- 原因：可能是大量手指边界附近的微小负值。
- 处理：同时检查`limit_clip_count`和`max_limit_clip_delta`；最大幅度超过门限才拒绝。

## 50步不是50个完整区间

- 50个waypoint之间有49个相邻区间，约`49/30=1.633s`。
- 不能把一个chunk错误理解成整整50/30秒，也不能连续执行完整同步chunk而忽略
  观测陈旧和边界不连续。

## 文件与目录

- `服务器IP`只是占位符，必须替换为真实IP；
- 路径用`/home/...`，不要写`//home/...`；
- 解压后先`ls`，不要根据压缩包名猜目录；
- Python模块多放一层会导致`No module named`；
- 整个项目重复复制到已有目标会形成`g2_robot/DM0.5/...`嵌套；
- 服务器修改不会自动同步到G2。
