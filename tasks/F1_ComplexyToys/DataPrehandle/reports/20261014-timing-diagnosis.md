## 第一优先级：队列配组的可证实等待

[当前配组代码](../../../../DAgger/F1/src/f1dagger/observation.py) 的 `queued_rows()` 使用每路 FIFO 队首：

1. 去掉首轮捕获之前或已经过旧的队首；任何一路为空就等。
2. 三路队首接收时间差大于 `camera_max_skew_s` 才丢弃最早一路并重试。
3. 一旦差值在范围内，即各取一张；不会继续在各路缓存里找时间更近的组合。

[开发树配置](../../../../DAgger/F1/configs/f1_09_hil.json) 为最大接收年龄 200ms、最大跨路接收时差 100ms。这是接受上限，并非实现了 100ms 内的曝光校准；本次未改任何门槛。

焦点原件 876 组，主图收到后等到整组可用的中位时间 **61.109ms**，左腕 **6.560ms**、右腕 **23.424ms**。三路原始接收时差中位 **58.130ms**、P95 **76.368ms**、最大 **96.861ms**。原有“整组可用后最多沿用 38.987ms”没有包含组装前的这段等待。

只在旧候选同一批 862 个 grid 时间点作对照：每路独立选择已保存且 `host_received_monotonic_ns <= grid_ns` 的最后一帧。统计如下，均为**接收时间**，不是曝光时间：

| 同一批 862 行 | 原整组取样：中位 / P95 / 最大（ms） | 独立取帧候选：中位 / P95 / 最大（ms） |
|---|---:|---:|
| 主图收到至 grid 的年龄 | 81.812 / 93.445 / 116.282 | 15.924 / 25.604 / 77.104 |
| 左腕收到至 grid 的年龄 | 29.795 / 38.665 / 86.066 | 16.627 / 32.898 / 36.529 |
| 右腕收到至 grid 的年龄 | 28.006 / 61.699 / 74.182 | 22.148 / 29.646 / 36.380 |
| 三路接收时间差 | 58.212 / 75.989 / 85.145 | 15.829 / 25.792 / 76.997 |

主图 847 行、左腕 214 行、右腕 352 行改选了其他已保存帧；主图通常向后选了两个 callback。**这些帧在 grid 前已经收到，但它们所属的原三路整组到 grid 之后才可用。** JSON 为每帧保存 `original_group_not_ready_at_grid`。因此：

- 它们不是 `host_receipt > grid` 的未来图片，但现有“等整组完成再给模型”的接口不能在当时提供这些帧。
- 该收益要求未来采集/推理具有独立相机缓存取数能力；还要计入实际复制、解码、预处理和请求组装耗时。
- 本候选只比时间配对，在整条原件保存帧中搜索，没有重新验证 Home、控制所有者、状态新鲜度、输入门槛和标签有效性，**不可直接当成训练批准清单**。
- 候选最大主图年龄仍有 77.104ms，说明逐路取帧不能消除所有空缺；缺失或未保存的图片不能恢复。
- 原件 876 组与 grid 862 行不是同一个样本集合；58.130ms 与 58.212ms 的区别来自统计口径，不应混用为同一对照。

**下一步实现入口：**先在独立离线候选中把“输入起点有效性”和“未来动作标签完整性”分开；保留单帧来源，再与将来的在线缓存接口使用同一选择规则。左腕 mask 应影响任务必需输入清单，而不是让它继续决定所有训练起点的切断。独立选“最近过去”并非唯一最优同步算法；还需比较以参考相机为锚点的过去帧组合、可用年龄与相互时差之间的取舍。

## 第二优先级：传输、回调与调度——目前不能唯一归因

焦点条目各路已保存帧的 host 接收间隔：

| 主图 | 33.308 | 38.120 | 265.002 |
| 左腕 | 33.290 | 36.007 | 163.968 |

这些是**最终保留下来的回调记录间隔**。中间回调若被配组丢弃，不会出现在图像 pack，故大间隔不必然代表设备整段时间没有发图。CLI 同时输出 callback 序号缺口，避免只看 FPS 推断原因。

主图相对各自首帧的 `(host 增量 − header 增量)` 最大变化 252.367ms，左腕 6.763ms、右腕 7.284ms。它支持优先检查主图时间标记/回调链路的异常；在源时钟未验证前，不能把 252ms 命名为网络延迟。不能直接相减 ROS header 的绝对值与 host monotonic 的绝对值，二者时钟原点不同。

**下一步取证入口：**读取运行进程已有的每路 pending 数、peak、drop reason、回调序号和时钟异常记录；将回调到达、入队、出队/配组、图像解码完成、观测 available 标在同一 host 时间轴。确需新增采集字段时采用有界诊断、保持原保护，并记录开销。随后才检查相机驱动发布、编码、ROS executor/回调积压、USB/网络或 CPU 调度与空缺的相关性。当前这四份原件没有完整发布/曝光/队列出入时间，不能分解各阶段绝对延迟。

## 第三优先级：源时间戳的语义与曝光证据

所有相机字段均标记 `f1_ros_header_unverified`。焦点条目主图相邻重复 header **46 对**，每对从 pack 读取并验证的 JPEG 字节都不同；两腕相邻重复为零。四条记录主图分别有 36、46、3、45 对，全部为不同字节。保留下来的记录中未发现源 stamp 倒退；这不代表驱动没有产生过被前置规则丢弃的倒退记录。

由此可确定：不能用“header 相同”直接把这些帧判为同一份图像 payload 或删除。不同 JPEG 字节也不能单独证明一定是不同曝光，因为还存在重编码等可能。

**下一步取证入口：**核对实际驱动 header 来自曝光、取流、编码还是发布时刻；记录它与主机时钟的映射、跳变与漂移。必要时用共享可见事件或可校准硬件信号同时出现在主视角/腕视角，并与机器人状态时间对照。延迟补偿必须建立在这类独立标定上，不能直接把 58ms 平移到图片或动作时间戳。
