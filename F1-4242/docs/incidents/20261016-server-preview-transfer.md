## 慢在哪里

1. 原协议每128KiB单独发一个JSON/base64请求，下载462.9MB需要数千次往返；返回视频也逐块传输。经SSH隧道，每个请求都有网络和HTTP处理开销。
2. 原全局限速2MiB/s，即使理想网络，数百MB下载也要数分钟；每块租约续期还要对任务JSON执行fsync。
3. 单worker串行处理历史积压；HIL整个运行进程active即暂停，包括待下一条的间隔。页面展示原图不意味着丢了视频任务。
4. 历史记录中，约459秒下载、20秒编码、59秒回传；同缓存独立编码22.019秒。时间属于10月13日样本，不能当作本轮测试。

认证修复及旧耗时的完整背景见[前一轮事故记录](20261016-preview-worker-auth.md)。

## 本轮修改

- 工作台claim协商source_block_bytes=1MiB，减少8倍下载请求；旧worker仍能按128KiB读取，新worker遇旧后端也回退128KiB。
- session_preview空闲双向上限改为8MiB/s，保留单流、逐块忙状态检查，并在限速等待后再次检查。介入视频保留2MiB/s。上传仍128KiB，保持现有256000字节请求体上限及同源认证边界。
- 租约仅在剩余不足90秒时续到120秒，20秒progress心跳继续持久化；不再每个下载/上传块重复fsync。重启后仍以磁盘租约验证，不绕过所有权或删除保护。
- 上传复用打开的文件句柄。下载增加返回偏移及块长度检查，最终仍验证全部来源SHA256和所有输出SHA256。
- 日志与发布收据记录queue_age_s、transferring_s、rendering_s、returning_s、total_s、paused_s及实际传输字节。queue_age_s是任务创建到本次领取的年龄，可能包含此前失败/部分传输，不能全解释成纯排队。
- FFmpeg编码、30fps审阅时间轴、CRF18、三路原始尺寸、原始数据与训练导出不变。没有启用F1本机编码，没有调机器人控制参数。

## 采集优先的边界

本轮保留原忙门控：HIL运行端还在运行，即使两条之间等待，也暂停传输；独立数采与已发现LXL录制同样暂停。完成一批并退出运行端后，自动继续。6000D对已下载完整的来源可以编码；回传等待F1空闲。

因此“几分钟出视频”应从允许传输、轮到该任务开始计算；持续采集和历史积压的等待不在这个承诺里。每次最多一个1MiB下载块，状态检查不是与START的实时原子屏障；启动瞬间可能还有已批准的小块在途，不声称零资源占用或已完成采集并发压测。保持这个保守门控是为了不在本次传输优化中引入新的采集并发策略。
