# F1-09 模型与驱动对照 · 2026-09-28

三轴模型方向修正已随 v18 / 0.6.2 部署。v20 已完成一次头部 J2 回程，随后用户完成 22 轴全身复位；模型物理标定仍未完成。

## 头部历史卡点（已完成一次回程）

全身复位的直接卡点是头部俯仰轴 head_j2：反馈约 −27.64°，现役驱动命令范围为 ±25°，复位目标是 0°。目标本身有效。2026-09-28 15:19 已通过原 ROS 合法边界目标完成一次向内回程，再按正常轨迹到 0°附近；首个边界目标不宣称限速平滑。15:28 用户完成全身复位。此段保留当时问题背景，当前验收以 [STATUS](STATUS.md) 为准。

网页 URDF 的 head_joint2 是 ±28°，因此这个反馈值可以落在模型范围内，却落在当前驱动范围外。不能据此断言机器人超过机械极限；也不能通过修改 URDF 让驱动获得恢复能力。

## 已确认的模型问题

### 三处双臂角度方向映射错误

原网页将 22 个 HAL 角度仅按关节名称、度转弧度直接应用到模型。独立核验确认下面三轴需要在模型坐标中反号：

| 真实反馈/目标角 | 模型角 |
|---|---|
| 左臂 J7 | −HAL 角 |
| 右臂 J5 | −HAL 角 |
| 右臂 J6 | −HAL 角 |
| 其余双臂关节 | HAL 原角 |

这只改变显示及模型 FK 的坐标转换。用户编辑值、HAL 反馈、下发指令、控制限位均保持真实角定义。原始 URDF 和 STL 不改。模型映射统一记录在 `configs/model_mapping.json`，发布清单和后端几何由准备脚本同步。

验证不依赖网页模型自证：先确认机器人原生 ForwardKinematics 服务只计算、不输出电机指令，再用每臂 8 个非退化虚拟姿态查询其响应。随后以真实响应矩阵检验模型；无需固定基座/工具标定的两姿态相对旋转角仍应一致。原网页映射不满足此条件；三轴修正后满足，独立回归容差为 0.005°。另一个含固定坐标转换的交叉检查最大姿态差为左 0.001629°、右 0.000951°。

这次没有移动机器人。当前三只腕轴接近 0°，修正对当前静止截图的影响可能很小，不能据此解释所有外观偏差。

### 模型几何仍不完全匹配

原生运动学使用 `ccs_m6_40.MvKDCfg` 的双臂 DH 参数，并未加载网页全身 URDF。对照发现：

- 网页模型一段名义尺寸为 311mm，原生配置对应长段为 314mm。
- 原生左右臂均有两处 18mm 的偏置；网页左臂相应原点中缺少该偏置，右臂保留了它。
- 修正角方向后，两套模型的位置关系仍有残差。它是模型之间的差异，不是用实物测量得到的 TCP 精度，不应直接作为机器人定位误差发布。

LXL 当前保存的 `0602_new`、meaxiao/Pico assets、Pico safety 与网页模型的关节 origin/axis 一致，主要差别是限位。换成这些同名文件不能自动修正几何。较旧 raw/0612 模型的部分身体轴方向相反，没有对应版本的零位说明，不应直接替换。

### 尺寸差异的进一步定位

16组原生FK响应的离线交叉检验进一步排除了“只是基座或工具坐标不同”：允许任意固定基座/工具平移后，左臂位置RMS仍为18.90mm、右臂1.93mm。旋转轴线间距也独立确认：原生DH左J3/J4、J4/J5均相隔18mm，原URDF左侧近似0mm；两侧沿J5的相邻共同法线间距为原生314mm、URDF311mm。

左 `joint4.x`、`joint5.x` 各增加18mm，是在当前坐标定义下可辨识的SDK对齐候选。但纵向3mm既可分配到 `joint5.y`，也可分配到 `joint6.z`，两者末端结果相同而连杆网格位置不同。没有CAD/link坐标说明时，不选择一个方案强行修改网格。也尚未证明当前DH型号对应本机两只实物机械臂。以上是模型间差异，不是实测TCP定位误差。

这一结论和22轴逐项来源、范围、映射、验收状态统一归入 [全身配置](JOINT_CONFIGURATION.md)。完整脚本和16样本留一检验在私有证据目录 `results/model_audit_20260928/tcp-origin-identifiability.*`。

### 标准复位左右手不等高的解释

2026-09-28 用户报告全身复位后模型左手较高。按标准 `pose_2` 理想目标离线计算，现用 URDF 的左、右 `arm_*_Link7` 原点在躯干坐标中的高度分别为 80.578 mm 和 56.424 mm，左侧高 **24.154 mm**；该姿态下躯干与底盘 Z 方向一致。

在内存计算副本中，只将左 `arm_L_joint4.origin.x`、`arm_L_joint5.origin.x` 各补 18 mm，高差降到约 −0.0024 mm。原生 DH 在名义共同安装坐标中的标准复位 TCP 等高。这说明现用 URDF 与原生运动学的几何差异足以解释网页约 2.4 cm 的左右高差；三个已修正腕轴在标准复位目标均为 0°，不是此次差异原因。当前模型资产尚未按此候选修改。

这不是实物左手误差的测量。用户随后保存的积木姿态左右角度非严格镜像，之后读取的 HAL 属于积木操作，不能拿来计算此前复位的实测误差。Link7 原点与含工具偏移的 TCP 也不是同一测量点。不通过改预设角度或增加经验角度补偿来让画面齐平。

补查15:28/15:29两次复位事件，旧版结果只保留部位级到位状态，未保存最终22轴角度。配置的关节到位容差为1°；因此 `at_target` 不能反推出实际角度恰好等于预设。15:43及之后的完整反馈已是积木姿态。缺失历史实测这一结论见私有 `reset-feedback-audit.json`，不能用后来的数据填补。

后续区分误差时，先用完整复位完成记录核对14个臂关节的有符号角度误差，再把同一次反馈输入现用URDF/原生模型分别计算。实物高度应在该姿态保持期间对照左右相同部位（例如腕法兰中心），避开左右夹爪开合或工具安装不同造成的外观差异。身体姿态也必须取同一份反馈。v22已补 `arrival_feedback` 终态字段，部署情况与字段边界见 [STATUS](STATUS.md)、[API](API.md)。

完整离线矩阵、输入与来源 SHA 位于私有 `results/pose_symmetry_20260928/`。此结论支持准备有来源的名义几何修正；要声称匹配实机，仍需两臂适用型号、安装/零点及同一实体测量点的依据。

### 身体和头部尚未实物标定

当前 22 轴中有 17 轴的模型范围与驱动配置不同，包括身体 J3 的范围方向差异。URDF 导出/修改历史和驱动使用目的不同，仅凭范围差异不能推断应翻转某个物理轴。

没有找到 F1-09 专属的身体/头部零偏、机构尺寸与模型坐标的实物标定记录。已有模型矩阵测试只证明软件按 URDF 正确计算，不证明 URDF 就是这台机器的准确几何。

截图中的棕色模型是编辑目标。身体 J3/J4/J5 从约 [−66.3,−79.4,−40.4] 只将 J4 改为 0，会在当前模型中形成明显前倾并穿过地面；这可复现模型结果，但不能代替实际机器的校准结论。后台地面检查也不是完整自碰撞或环境规划。

## 上游转换为何不能直接照搬

Pico 的同步到 Placo、发送到 HAL、安全检查三条路径使用的角度转换并不一致。某些路径还带启动参考值或相对控制补偿，不能把其中一段公式直接搬入网页。此次模型修正依据原生计算服务的独立响应；没有修改 Pico、LXL、原驱动或其控制映射。
